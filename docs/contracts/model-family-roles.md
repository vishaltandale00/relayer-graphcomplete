# Model-family roles producer contract

New family members carry `roles: [{ name: string, description?: string }]` on their exact provider/model identity. Exactly one member has the reserved, lowercase `orchestrator` role. Other labels are user-defined descriptive metadata; a member may have multiple labels. Family order is preserved.

New execution and admitted plans carry `schemaVersion: 2`. Every route, including the exact `orchestrator` pointer and every roster route, carries a `roles` array (empty is valid for specialists). The pointer must equal the unique orchestrator-bearing roster route. Roles, order, family revision, identities and adapter versions are frozen at admission. Specialist unavailability may filter the roster; orchestrator unavailability refuses execution.

Historical plans without `schemaVersion` are version 1. Their routes omit `roles`; retain the existing JSON serialization and `relayer.harness-model-plan.v1\0` digest. Version 2 signs the unsigned plan including `schemaVersion` and all roles with `relayer.harness-model-plan.v2\0`, using the shared field-order serialization: `schemaVersion`, `familyId`, `familyRevision`, `orchestrator`, `roster`, `harnessPolicyDigest`. Each route orders `roles` first, then `providerId`, `adapterId`, `accessContract`, `modelId`, `adapterImplementationVersion`; each role orders `name`, then optional `description`. Array order is retained. Optional fields must be omitted when absent; explicit `null` roles or descriptions are invalid. Version 1 omits the schema/role fields and retains its original field order. Unknown versions and mixed-version role fields fail closed. Both Rust portable export/import and the harness host must use this contract. Historical receipts never determine a future orchestrator.

Producer fixtures live in `test/fixtures/model-family-roles/`. New fixtures include exact named connections, an orchestrator with an additional specialist label, and an unlabelled specialist.

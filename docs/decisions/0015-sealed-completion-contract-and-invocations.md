# ADR 0015: Sealed completion contracts and reusable Invocations

Accepted product direction for #632, delivered by #658, #659 and #660. Implementation and verification remain gated independently. A canonical InteractionNode owns one immutable versioned CompletionContract sealed atomically by trusted preparation before capability issuance and inference. Exact recovery preserves the original input, authority, requirements and digest; it never upgrades old preparations. The executing completion observes the entire contract through the typed graph input API.

The contract contains `schemaVersion`, normalized `input`, typed `authorities`, `returnRequirements` and `digest`. Runtime credentials, sessions, transient execution state and harness switches are excluded. All exceptional permissions share one authorities field. Universal graph integrity and existing graph read rules remain graph-owned. Input includes exact accepted answer identities and snapshots; presenting occurrence remains validation/audit provenance, rather than an extra semantic answer identity. One interaction cannot answer the same accepted action twice.

## Advance and Return

For this contract, Advance validates the complete prospective Return transaction, including authorized staged accepted-history changes. It publishes only the owned Current Layer and its immutable revision. Accepted-history changes remain staged until Return, which revalidates concurrency preconditions and publishes them atomically with the Returned Layer. Return ends this interaction's authoring, not the user's overall task. Rejection remains repairable and retains the prior Current Layer; stop/failure retains progress without a Returned Layer. Revision zero is the interaction anchor before any response Layer is published.

## InvokeAction and Invocation

An InvokeAction is an immutable callable definition owned by one response Node. Newly authored actions permit one call by default. Explicit reusable actions permit multiple distinct Invocations for a meaningful repeated-use workflow. An Invocation is a separately stored durable call reference and binds to at most one child InteractionNode. Exact-key recovery remains the same call, not another use. The result does not convert the definition into another action type. `subcomplete` records the parent relationship from the exact source response Node under the InteractionNode's sealed rules. Author, creator, activator and presenting Layer are provenance. Accepted Node/Layer definitions remain immutable while their read presentation can join separately stored Invocation results. Existing frozen definitions retain their original reuse semantics.

An active author may call an action on its own draft Node before Advance. New child input captures the exact action definition and explicit arguments/context. It does not inherit the parent's session or authority. Parent and child terminality are independent, and graph access to the recorded relation/result follows existing graph rules. A later authorized InteractionNode may activate a prepared reference. Dependency conditions are exact guards on actor-issued activation; GraphComplete and the harness host add no semantic scheduler. Providers retain native recursive execution and coordination.

## Enclosing-analysis integration

Each invoked SubCompletion must integrate its contribution into the overall analysis connected to the response Node owning its InvokeAction, under its own sealed InteractionNode's authority and requirements. The analysis may contain Nodes with nested content Layers. Recording an isolated child result or adding a result control is insufficient: details and enclosing comparisons, recommendations and conclusions must remain coherent on each Return. Previously accepted Layers remain history; this does not authorize general edits or inherited parent authority. Return must publish the authorized integration atomically with the child result, while Advance leaves accepted-history changes staged. Deterministic integrity checks cannot substitute for judgment of semantic coherence.

The first human-gate demo defaults to one SubCompletion at a time. A reusable example uses meaningful distinct destination inputs and separate result controls beside Invoke. This requirement does not add timed activation or a scheduler. The precise integration seam and its checkpoint proof must be qualified before delivery is claimed.

Field-plus-Invoke snapshots the named committed input-draft revision through trusted preparation. Existing accepted question/value validation runs before the child contract is sealed. Successful submission clears the connected submitted fields and removes those attachments from the pending Send draft. Unrelated attachments and edits committed after the captured input snapshot remain intact. Refused submissions retain their inputs. Exact-key recovery after clearing still uses the original frozen arguments, never new draft values. The accepted callable stays unchanged. Frozen child input is read from the exact graph-owned Invocation rather than duplicated as mutable Product authority.

An Invoke input binding explicitly identifies the input actions consumed by that callable. Proximity on a Node or in compiled markup is not a binding. Activation saves the connected current values and selects only those arguments from the exact draft revision, and trusted preparation refuses missing or extra arguments before sealing. An input may connect to multiple Invokes, but successful submission clears its captured value; another call requires fresh input. Product presents connected fields together with the Invoke control. Existing frozen preparations retain their original argument snapshots. This clearing decision supersedes the earlier copy-without-consuming Send-draft behavior.

## Authoring declaration references

Input and Invoke remain separate action kinds. TypeScript `inputActions` and Python `input_actions` can name exact Input declarations before database IDs exist. Visual programs require the referenced Input to be mounted on the same owning Node; the Prime wire representation uses an explicit tagged client-key reference, resolved against the program's mounted declarations. Placement never infers a connection. Ordinary action authoring resolves dependencies with their stable keys before writing Invoke's canonical `inputActionIds`; numeric bindings remain compatible. Visual compilation does not create actions, so nodes/layers still precede the explicit action write. Invalid references are refused before transport where locally observable. Native ownership and acceptance validation remain authoritative. A late transport or native refusal may leave recoverable draft Inputs, not an atomic multi-action write. This authoring convenience grants no authority and does not change reuse policy or execution.

## Across-execution and replay successors

The first slice includes versioned, inert reusable-call portability in conversation and share snapshots. V4 captures each call's export-local identity, immutable callable/source provenance, frozen arguments, lifecycle, accepted Current, and distinct Returned association from one coherent graph snapshot, including graph-prepared calls without a Product turn. Uncalled callable input bindings are preserved. Imported call history cannot execute, prepare native calls, or mint CompletionContract authority; canonical graph imports receive fresh identities while portable provenance remains coherent on re-export. Legacy Action origins retain their one-shot uniqueness and are never used for reusable calls. Old readers reject V4 rather than silently dropping call history. Local viewer/format qualification and deployed hosted-format support are separate evidence gates; live publication is not implied.

#659 owns retries and explicit logical Stop: one Invocation and child identity, append-only ExecutionAttempts, retryable failed/interrupted attempts, final settlement on Return or explicit StopInvocation. A stopped logical Invocation is never reopened. No mandatory semantic retry cap is imposed. An exact-attempt dependency may observe that attempt's terminal outcome; an overall dependency observes final Invocation settlement.

#660 owns inert Eval Replay. Capture retains contract/input evidence, graph identities, Invocation attempts and outcomes, Current/Returned Layers and exact running-at-capture state. Import never creates graph execution authority, and judgments live outside the captured graph.

## Supersession and compatibility

This supersedes ADR 0011's terminal-only requirement enforcement for newly sealed contracts, ADR 0010's action-global invoke conversion for new Invocations, and ADR 0008 input's presenting-occurrence answer identity for new sealed input. ADR 0008 temporal current, provider-owned execution and trusted terminal observation remain applicable except where the new contract makes graph parent/result relations explicit. Existing frozen permissions, accepted conversions and legacy answer snapshots remain readable under their exact old versions; no authority is synthesized on reopen. Rollout must distinguish new sealed preparations from genuine pre-contract legacy records and reject missing contracts for new-format records.

## Input acceptance and chat ownership (approved 2026-10-07)

Standard Input controls implicitly accept the current answer unless the user chooses Undo. There is no separate check mark. Send saves and snapshots only unbound answers; an accepted Invoke binding keeps its inputs outside ordinary chat. Invoke saves and snapshots only its connected answers. Undo restores the prior saved answer or clears a new one. Pending edits survive node navigation. Authored selection-change and text-blur saves remain supported.

Before awaiting persistence, the renderer captures exact occurrences, values and edit epochs and reserves the submission boundary. Newer or unrelated edits survive cleanup. Trusted graph classification owns the ordinary Send subset; the product transaction checks its draft revision and digest and consumes only those exact rows. Bound-only empty Send is refused. This supersedes the earlier per-input confirmation requirement, without changing graph validation, immutable submitted input, or exact-key recovery. Repeated-use Invoke UX remains outside this V1 human acceptance gate; retained historical calls keep their frozen semantics.

Ordinary Input answers follow the approved annotation response-link behavior: trusted preparation derives exact source-Node Navigate grants and requirements from validated answer occurrences. Shared source Nodes are deduplicated. Recovery retains the original sealed contract rather than deriving new grants for old records.

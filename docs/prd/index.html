This PRD specifies two product packages. Both packages are in the relayer-graphcomplete repository. They ship together as one Relayer product.

  1. Relayer Desktop is the local application. It provides projects, threads, providers, persistence, Git worktrees, the graph interface, updates, evaluations, and saved-result replay.
  2. Relayer Harness contains the graph engine, complete(inputGraph), harness host, supported implementations, graph tools, and evaluation suites.

The repository is a monorepo. Relayer Desktop and Relayer Harness have separate package and runtime boundaries. V1 does not put them in separate repositories.

V1 does not include a general harness desktop, arbitrary harness plug-ins, or a custom conversation-view framework. These items are deferred. The Relayer product must first show that a reusable interface is stable.

The Product capabilities come first. Contracts follow the product behavior. Evidence and acceptance appear last.

1. Product model and scope

The delivered product is Relayer Desktop with its pinned Relayer Harness. A user connects an agent credential and creates a thread. The thread can use no folder or a project. For a Git project, the user can select the local checkout or a new worktree.

Relayer has a harness- and provider-agnostic product contract. Product workflows use stable catalog identifiers and the same Complete boundary. A supported harness or provider still requires an explicit adapter, declared compatibility, tests, and release inclusion.

The user sends interactions and can stop or retry the work. The user can navigate accepted history and reopen saved threads. The user can also install desktop updates.

Each accepted Complete call saves a graph response. Relayer Desktop shows the returned layer as movable nodes. Each node has an icon and a title. The right inspector shows the selected node details and actions. The user can navigate to prior nodes or attach them to a later message.

A harness build can ship only after all required checks pass. These checks include deterministic tests, live evaluations, saved-result replay, and human visual review.

Relayer Desktop owns the user-facing product:

  • local profile and secure credential storage;
  • projects, no-folder chats, threads, folder permissions, checkouts, and worktrees;
  • app-server lifecycle, composer shell, history navigation, stop/retry, settings, local persistence, recovery, packaging, updates, and release channels;

  • product capabilities for filesystem, Git, secret references, app data, and cancellation.

It does not implement agent recursion, decide graph semantics, or own Complete prompts and evaluation rubrics. It renders and interacts with graph state only through the graph engine's stable product APIs.

The GraphComplete runtime owns the graph and harness contract:

  • the Rust graph engine, local graph API, schemas, layers, actions, accepted graph state, persistence, migrations, and read/write authority;
  • typed TypeScript and Python graph clients used directly by harness code;
  • the persistent Node harness host, Complete, supported harness implementations, and provider adapters;
  • the evaluation runner, cases, deterministic checks, quality judge, and replay bundle.

These runtime components are implemented and evaluated together. They remain separate packages. The graph engine is authoritative. Clients must not open its database directly. The harness host must not implement graph rules. The evaluation runner must not contain a second product or Complete implementation.

The Rust app server creates product interactions and calls the same persistent Node harness host used by evaluation. It persists the accepted result and serves it to the renderer.

1.4 Relayer Desktop and Relayer Harness interface

The canonical external boundary is one Complete call. inputGraph is a small pointer. Its root is one already-prepared canonical user-interaction node. It is not a serialized copy of the project graph. Human-root product code prepares that interaction from the user event. Trusted recursive adapter code prepares or exactly recovers a child from a sealed Invocation and its exact callable snapshot. The active author may call its own draft before Advance. Legacy calls retain their original published-occurrence rules. Both paths then enter the same Complete module. Model-authored code cannot substitute an arbitrary interaction-shaped node or mint child authority.

The root package exports this boundary and a process-owned configuration seam for injecting its trusted completion runtime. The Rust app server reaches the same executable seam through the persistent HarnessHost.

interface RelayerHarnessClient {
  complete(inputGraph: { interactionNode: NodeReference }): CompletionHandle;
}

interface CompletionHandle {
  readonly completionId: GraphId;
  readonly current: CompletionCurrent;
  readonly result: Promise<ResolvedGraphLayer>;
}

interface CompletionCurrent {
  snapshot(): Promise<CompletionCurrentSnapshot>;
  next(afterRevision?: number): Promise<CompletionCurrentSnapshot>;
}

type CompletionChange =
  | { child: CompletionHandle; current: CompletionCurrentSnapshot }
  | { child: CompletionHandle; error: Error };

interface CompletionWatch {
  readonly settled: boolean;
  changes(): Promise<readonly CompletionChange[]>;
}

interface CompletionTerminalError extends Error {
  readonly completionId: GraphId;
  readonly lifecycle: "stopped" | "failed";
  readonly current: CompletionCurrentSnapshot;
  readonly reason: string;
}

Complete returns one handle after trusted preparation establishes or recovers the canonical completion identity.

Preparation is a separate step, and it is the authority step. Agent code publishes an accepted invoke action, calls prepareComplete(action), then calls Complete.

complete(inputGraph) establishes no identity of its own. It requires an already-prepared interactionNode and rejects anything else.

Server-side capability derives from the published invoke occurrence. Exact-retry recovery keys off that same occurrence.

current observes the durable GraphComplete pointer. result resolves only from GraphComplete succeeded state and its canonical final layer.

A model turn or provider process ending does not resolve it. Stopped and failed completions retain their last current and reject result with a structured terminal error. They never fabricate a final layer.

A never-settling promise is not the contract. An awaiting agent must be able to observe child termination.

The parent's own invoke action stays unresolved and navigable to the child's retained current. An unresolved invoke never means an unsettled handle.

An agent may stop a completion whose invocation names it as the direct source. Grandchildren, siblings, and human or product callers may not.

handle.stop(reason) is that agent-only control. The stopped child retains its current and reports stopped.

Observation is delivered as current-pointer revisions only. There is no token streaming, no partial-layer publication, and no additional event kind.

An awaiting agent performs no repeated polling. The server holds one observation open and answers when the awaited completion advances, filtered to that caller's grant.

current.next(afterRevision) answers when one child's current moves past that revision or ends. A watch over the children an agent launched reports each such change as one event.

A watch may lose a child, for example after a refused start. It then reports that child once, with the error instead of a current. The watch does not watch that child again, and settled counts it as ended. The watch never invents a current for it. This report is not an observation event, so observation stays current-pointer revisions only. One child's failure never holds back its siblings' events or the watch settling.

The TypeScript and Python clients apply one rule to broker refusals, so a parent learns the same thing in either language. The error names the refusal's HTTP status, even when its body is not JSON, such as a proxy's error page. A client refusal (4xx) also carries the broker's string error message when it has at most 200 UTF-16 code units and no ASCII control characters. A server failure (5xx) never carries broker detail. Following a redirect, neither client sends the broker token to another origin (scheme, host, or port); it is kept only within the broker's origin.

A launch can fail after the product claims its child, for example when capability activation fails or preparation ends ambiguously. The product then fails that child in both stores with a safe reason. Once it has failed, an exact retry of the same launch starts nothing and reports it.

Restart never reattaches. Interrupted active completions fail safely with application_restart and keep their retained current. This includes an agent's child that the product recorded but had not yet launched. A user's invoke action never runs an agent's child.

No provider is asked whether its execution survived. Complete is never re-called as crash recovery for an already-started execution.

The app server creates the human-root interaction and passes its pointer to Complete. A supported recursive provider adapter derives the prepared pointer from the invoking completion and exact published invoke occurrence. It then passes that same pointer to Complete. The selected harness uses its bound graph client to construct nodes, edges, layers, and actions, then returns with current.return(layer) or the compatible graph.submit(interactionNode). The accepted result includes the fully resolved first layer so the desktop can display it immediately without a second request. The graph engine persists the same layer and serves later navigation. A model turn ending without Return is failure, never success.

The product stores one named harness on the thread. Model is the primary composer choice. Advanced shows compatible harness configurations before thread creation. The pinned harness becomes read-only after creation.

The selected harness owns model execution and provider-session reuse. Each explicitly supported recursive adapter, including Codex and Prime Agent, owns its provider-native child launch or binding, concurrency, waiting, messaging, and session behavior. GraphComplete, Relayer product, and the harness host do not add a recursive runnable queue, automatic parent wakeup, or incorporation policy. Provider adapters own authentication and model discovery. Relayer product records do not expose raw credentials, provider flags, runtime sessions, or implementation-specific recursion policy.

Secret-backed provider execution keeps authentication credentials available to the provider process. Model-requested shell tools must not receive the provider API key or endpoint. Concurrent executions preserve this boundary and retain their assigned graph capability. Subscription execution keeps its existing runtime configuration.

1.5 Items not in V1

V1 does not include arbitrary harness adapters, third-party conversation views, a generic agent protocol, or a public multi-harness conformance kit. Eval may compare supported harness, provider, and model configurations, but every run still exercises the Relayer product contract. A general platform should be reconsidered only after repeated implementations reveal a concrete reusable seam.

2.1 First launch

Relayer uses one implicit local profile. First launch opens Agent setup and, after a valid configuration is saved, opens the normal New thread window. An optional Relayer account offer may appear only after that local workspace is usable. Folder, project, and account choice are not blocking onboarding steps.

The setup surface is one focused Agent login card. Codex and API key are presented as horizontal login-method choices, followed by the credential and model controls for the selected method. The form should not split setup into equal Harness and Agent login columns or stack alternative methods into a long vertical option list.

Agent setup does not require a harness choice. After connection, the New Thread composer presents Model as the primary execution control. Its Advanced tab contains compatible harness configurations.

A successful provider connection with at least one execution-eligible model creates one product-managed, provider-scoped model family before setup completes. First launch selects the unique valid provider, family, model, and default harness route atomically; it does not require custom-family construction. Product policy admits only reviewed synchronous text or agent models and fails closed for unknown capabilities. It applies a versioned provider preference before provider order and caps the managed family at five models. OpenRouter policy version 1 is the explicit three-model general-agent roster deepseek/deepseek-v4-pro-0813, qwen/qwen3.8-max, and z-ai/glm-5.3, in that order. Vercel AI Gateway policy version 1 provides the equivalent roster using its catalog identities: deepseek/deepseek-v4-pro-0813, alibaba/qwen3.8-max, and zai/glm-5.3. Both policies omit missing or unavailable entries rather than falling through to arbitrary catalog order.

Codex production policy version 4 prefers GPT-6.1 Sol, GPT-6 Astra, then GPT-6 Luna before other provider defaults. Sol uses medium reasoning in the shipped Codex harness. Claude subscription choices are Sonnet 5.5, Opus 5.5, and Fable 5.1. The release-owned Claude Code 2.1.286 runtime executes these choices through its native sonnet, opus, and fable aliases. Provider connection results

Each provider has a connection generation. Connecting a provider starts it. Completing a reconnect, signing out, and removing the provider each advance it in the same write.

  • PROV-002: A superseded provider result is inert. A catalog refresh, a recovery and a reconnect's discovery each carry the generation they started with. Suppose a reconnect, sign-out or removal happened since, or the provider left active. Then the result changes no family, default, catalog or adapter. The app server refuses such a publish inside its write. User actions supersede automatic ones.
  • A refresh uses the provider's catalog adapter as it is when the refresh runs, not when it was requested.
  • A cancelled or failed reconnect leaves the provider refreshable. It keeps a live catalog, or its recovery path if the provider could not be activated.
  • A cancelled or failed reconnect records the signed-out state with the next generation, as sign-out does. Every result still in flight becomes inert.
  • If that record fails, the reconnect keeps its sign-in, as an unknown outcome does. The next refresh settles the provider's state.
  • A cancel keeps only a sign-in that exists. When the account reads signed out, there is nothing to keep. A check that cannot answer in time leaves the outcome unknown.
  • A sign-out the app server confirmed during the reconnect is the exception. That sign-out stands, and the reconnect's sign-in is removed.
  • Recovery never uses the runtime a pending reconnect is signing in. Until that reconnect settles, recovery reports the provider unavailable.
  • No catalog refresh starts or publishes while a reconnect is pending. That includes preparing its runtime and starting its sign-in. When an installed runtime is available, reconnect starts browser sign-in in parallel with runtime setup. It returns the login handoff while setup runs. The connection remains pending until setup succeeds and authentication is confirmed; setup failure follows reconnect failure recovery. A missing runtime is installed before its native login starts. Cancellation and sign-out remain available while setup runs.
  • Sign-out records the disconnected state itself. It does not wait for a catalog refresh.
  • A refused sign-out or reconnect rereads the generation first. Sign-out then retries once; a refused reconnect fails, and the next one starts current.
  • PROV-007: Connect is all-or-nothing. A catalog adapter, credential or managed family exists for a provider only once its definition is saved. A failed or cancelled connect leaves none of them. Nothing publishes for a provider before its definition exists.
  • Harness readiness is kept per harness, not per provider, so PROV-002 and PROV-007 do not cover it.
  • The app server may save a new provider but lose its answer. Relayer then reads the provider back and keeps it. If that read fails too, the next launch keeps the credential only for a saved provider.
  • The app server may commit a reconnect but lose its answer. Relayer then rereads the generation. Relayer keeps the reconnect and its sign-in when the reconnect provably advanced it.
  • That proof needs the generation one step past the one the reconnect read at its start, with no sign-out since. An unmoved generation means the reconnect failed.
  • A lifecycle write whose answer was lost may still commit later. Until a later answered write advances the generation, no reconnect is adopted on that proof.
  • Without that proof, the reconnect's outcome is unknown. Relayer keeps its sign-in and reports the reconnect as failed. The next refresh settles the provider's state.

Provider execution access

A turn holds its provider's execution access exactly as long as its native agent runs, unless the turn is force-stopped. The access ends when the native turn settles, or within ten seconds of a force-stop. It does not wait for Relayer to record the turn's outcome.

  • PROV-004: Provider access is never released while the native turn that uses it still runs, unless that turn is force-stopped. Remove, sign-out, and reconnect therefore never run under live native work that was not force-stopped.
  • A turn cannot take provider access while that provider's reconnect is pending, or once Relayer has begun to quit. Quitting closes provider access before it waits for other services.
  • After a sign-out the app server did not record, a turn cannot take provider access. This lasts until the app server records the signed-out state, or Relayer confirms a sign-in again.
  • This block lasts while Relayer runs. After a restart, the startup refresh reads the account and records its state.
  • When Relayer gives up on a running turn, it cancels the turn. The access is released once the native turn settles, or within ten seconds of a force-stop.
  • A turn cannot start on an admission whose release has already begun.
  • PROV-003: Removing a provider finishes without a restart once nothing is actually running on it. This holds after an application restart and when Relayer could not record a turn's outcome.
  • Once Relayer stops waiting on a turn, the turn's attempt no longer blocks removal, even when Relayer could not record the turn's outcome. Access a native turn still uses stays held until that turn settles or is force-stopped.
  • An attempt whose interaction already failed or stopped, such as through an expired or aborted approval, ends with that outcome. An attempt pending reconciliation keeps its outcome open until canonical graph output settles it.
  • After a restart, an attempt that ran in the previous process no longer counts as running. Its interaction may stay pending reconciliation, and its canonical output is still recovered when its thread is opened.
  • A recursive child still unwinding when Relayer quit is checked before startup finishes removals. A child the harness no longer runs ends first. Startup waits at most three seconds for all such checks. A child still running or unreported keeps its provider until its run ends.
  • One provider's removal or cleanup failure never stops Relayer from starting or other providers from activating. The failure is recorded. A removal that fails before its tombstone stays pending for the next start. Cleanup that fails after it is swept at the next start.
  • A cancelled turn still running after two minutes is force-stopped. Only that turn stops; other turns and children on the thread keep running.
  • The force-stop ends that turn's process or session. Its access is released within ten seconds.
  • A force-stopped turn ends as a settled cancellation. A turn the user stopped is recorded as stopped, and the force-stop appears in its diagnostics.
  • A root turn force-stopped while its native conversation ran is not resumed. The next root turn starts a fresh one and still receives the graph context unless AGT-012 requires native continuity, in which case continuation is refused.
  • Prompts carry only the current turn, so a native conversation is kept whenever the selected provider can resume it (#584).
  • Providers that share a native home keep resuming the same conversation. A provider in another home cannot resume it.
  • When the native conversation cannot be resumed and AGT-012 does not require native continuity, the turn still runs in a fresh native session. The turn's diagnostics record that native history was unavailable, and why.
  • A reset notice makes the reset visible. It does not restore the lost context.
  • These rules decide only resumption for the provider the product selected. The legacy compatibility policy decides which providers an existing conversation may select.
  • Force-stopping is best effort. If it fails to end the turn, Remove can proceed while that turn still runs.
  • A harness that cannot force-stop keeps a cancelled turn's access until the turn ends.
  • Remove's waiting state for running turns and an explicit Stop turns and remove action are planned.

Electron main is the only Sentry authority. Renderer and child processes submit typed records through generation-bound local capabilities.

Only a verified account generation enables admission. Every other account state creates no request or queue record.

Main derives one stable identifier with SHA-256("graphcomplete-sentry-user-v1\0" || UTF-8(Auth0 sub)). Callers cannot supply identity or transport configuration.

  • V1 reports unhandled process crashes, supervised-child startup failures, supervised-child unexpected exits, and the closed shared-thread failure exception below.
  • Share export, oversize, upload, service, and unexpected deletion failures may report from Electron main. Cancellation, sign-in requirements, quota limits, every other handled operation or validation failure, denials, retries, disconnections, warnings, information, and success never report.
  • The handled-share record contains only its user-visible attempt reference, closed stage/code, and optional oversize byte count. Diagnostics add sanitized app frames, optional HTTP status, and a closed network error code. It retains existing safe app diagnostics and the main-derived pseudonym. It excludes title, project, conversation content, credentials, raw errors, and request data and deduplicates by account, reference, stage, and code. Electron main persists that deduplication key before reporting and suppresses reporting when persistence fails.
  • Share diagnostics retain the original exception's first available approved app stack. Electron main inspects at most four error/cause objects. HTTP status is an integer from 100 through 599 or absent. Network codes use a fixed allowlist; unknown codes are omitted. Raw cause messages, hosts, URLs, bodies, and headers never report. Diagnostic inspection cannot change the share result.
  • Legacy share reports without diagnostics remain valid. Queued reports still require the existing same-account, release, and platform checks; cross-release replay is unchanged. Diagnostics do not change deduplication or enter the durable share attempt record. Sentry receives frames in oldest-to-newest order.
  • Accepted JavaScript frames use application-relative module names. Each event keeps at most 32 frames and 256 characters per module name.
  • Rust frames name only approved workspace crates and modules. Absolute paths and third-party frames are rejected.
  • Every module name must match the exact packaged-module inventory. Valid-looking invented names are rejected.
  • Approved fields are stable failure code, code-owned message, frames, component, operation, release, environment, OS, architecture, and pseudonymous identity.
  • Prompts, graph or model content, paths, commands, environment data, credentials, requests, URLs, logs, and raw errors are forbidden.
  • Breadcrumbs, attachments, replay, tracing, profiling, performance events, default PII, and automatic request context remain disabled.

The encrypted queue holds at most 32 records and 256 KiB. Records expire after seven days, and overflow evicts the oldest record.

Any corrupt queue is deleted. Retry requires revalidation of the same Auth0 subject and never creates recursive telemetry.

Logout or account replacement disables admission and deletes the old queue before account presentation changes.

Release identity comes only from immutable sealed package metadata. Electron main supplies the Sentry environment from its validated current update channel.

The versioned shared privacy corpus covers every process seam and forbidden field. npm run evidence:telemetry runs its deterministic portfolio.

Live Auth0, packaged storage, system-browser, upload, and symbolication proof runs only for Preview or Stable release candidates.

Each target proves only its native platform: macOS Apple Silicon, macOS Intel, or Windows x64. Missing target evidence remains indeterminate.

User goal: Reopen a thread after navigation or restart.

Product rule: Relayer persists accepted state and explicit interrupted states.

Observable result: Saved threads reopen from Chats or Projects.

8.1 Saved threads and navigation

The sidebar contains New Thread, Chats, and Projects. Chats contains no-folder threads; Projects contains saved thread entries. The sidebar stays visible at every width. At 760px or narrower it starts as a collapsed icon rail. Its existing toggle expands the same sidebar in normal flow. The workspace fits the remaining width. Explicit expansion stays open while the viewport remains narrow. Settings and Account stay in the footer, with icons while collapsed and labels while expanded. A Download update icon appears when an update is available.

The sidebar is a compact list. It is not a recursive graph tree. A child conversation can become a saved sidebar entry. The sidebar does not show its full ancestry. Graph breadcrumbs show this ancestry.

The header shows the current thread title, scope, and backward/forward turn controls. The composer remains the place to send, stop, and attach context. There is no separate active run dashboard.

A status symbol follows the thread title only while the thread is Running, Stopping…, Needs approval, or Failed. There is no symbol when the thread is idle, stopped, cancelled, or accepted. The symbol's shape, tooltip, and accessible name carry the state. The prompt card keeps its turn-level status pill.

8.2 Local persistence and restart recovery

Product data is local and disk-persisted:

  • profile and non-secret settings;
  • provider configuration references;
  • projects and authorized-folder metadata;
  • thread/sidebar projection;
  • user-interaction nodes, graph data, accepted snapshots, and execution status;
  • update state and schema version;
  • optional developer traces when explicitly enabled.

Current recovery: Startup marks interrupted ordinary and action interactions as failed. Ordinary work continues through a follow-up. One-shot action retry is unavailable.

Persistence uses atomic writes or transactions. A crash may interrupt an in-progress Complete call, but it must not corrupt the last accepted graph. On reopen, accepted turns render immediately; an interrupted interaction is marked stopped or failed and retryable. Recovery is a reliability requirement, not a primary product concept or prominent settings category.

A published thread snapshot is not local product data. It survives sign-out and removal of local data.

10.2 Desktop application updates

Signed desktop updates are essential V1 distribution infrastructure.

  1. The app checks a configured HTTPS release channel for a signed manifest. It checks shortly after launch and again on a recurring background schedule.   2. It compares version and schema compatibility without blocking the user.
  3. It downloads in the background and verifies hash and publisher signature.
  4. When an update is available, a small highlighted circular download icon appears at the bottom-right of the sidebar. No version number or update label is permanently shown.
  5. Clicking the icon opens one compact prompt describing the update with a single Download update action and a dismiss control.
  6. Download and verification occur without blocking chat. Installation is deferred while Complete is committing graph work.
  7. When an update operation fails, Settings and the update prompt show the failed operation and a safe explanation with a diagnostic code. Retry clears the prior failure when discovery resumes. If migration or startup fails, Relayer must fail closed. It must not change the last recoverable database state. It must offer a recovery procedure. 11.2 One cumulative graph and four records

Relayer product storage owns projects and threads. Graph core does not create project records, thread records, project graphs, thread graphs, graph spaces, or a separate interaction graph. It stores the product-owned positive-integer projectId and threadId on graph records as provenance. Threads with the same project ID read the same accepted graph records. A no-project thread stores projectId = null and reads only records carrying its own thread ID, so standalone threads never share graph records.

Every user turn is represented by one canonical user-interaction graph node. That node's NodeReference is also the product interaction identity after integration; no second interactionNodeId is synthesized. The host supplies project/thread IDs when it asks graph core to create this node. A graph capability stores only the node reference. On every graph request, the engine calls GraphDatabase::writer_for_subgraph(node) and derives read visibility plus draft-write authority from the persisted node.

The clients are object-oriented because models are better at constructing and repairing nodes and layers than remembering large collections of raw IDs. A local node object receives its stable reference after its first successful submitNode. Resubmitting that same local object updates its current draft rather than creating a duplicate. The draft's checkpointed authored detail follows a three-state rule. A resubmission that omits authoredDetail retains the stored package. authoredDetail: null clears it, and a package replaces it. The TypeScript client sends null only after an explicit detailAuthoring.clear(); an untouched empty builder omits the field, and clients that never mention the field retain. A different local object that reuses a stable client key updates that same draft, including its package. A rejected edit preserves the last valid draft and returns a field-specific error so the harness can repair and resubmit it.

createEdge accepts node objects or references. Creating an edge from a new node to an accepted historical node does not resubmit or modify the historical node. Adding an accepted node to a new layer also does not modify it. Accepted historical records are immutable; a changed explanation is represented by a new node connected to the old node.

graph.submit(interactionNode) is the deterministic completion boundary. It derives exactly one interaction-authored root expand action.

On desktop the harness host runs in-process in Electron main; in Eval it runs in the Node Eval host. It is not a separate child process. It resolves a small code-owned implementation map and lazily constructs one harness object per thread:

If the Node process or provider session expires, the host recreates the object from stored configuration and opaque provider resume state when available. Session reuse should be used when obvious and behavior preserving, but continuous GraphComplete context must not depend on it.

Only human root turns count toward a thread's one active turn. A user's message and a user's invoke action are human root turns. A child that an agent launched never blocks the next human turn. 7.2 Authored node actions

Every node action except + is authored by the harness on that node. Authored actions appear inline first; the universal attach-context + is the final control in the row. An action declares:

type NodeAction = {
  id: string;
  actionKey: string;
  sourceNodeId: string;
  sourceLayerId?: string; // required for node-level authoring; hidden from users
  label: string;
  kind: "navigate" | "invoke" | "input";
  relation?: "expand" | "reference"; // required for navigate
  targetLayerId?: string; // required for navigate; a layer may contain one node
  interactionTemplate?: {
    kind: "message" | "node-action";
    text?: string;
  };
  input?: {
    control: "text" | "single_select" | "multi_select";
    prompt: string;
    options?: Array<{ key: string; label: string }>;
    minimumSelections?: number;
  };
};
  • navigate opens an accepted layer without Complete. An expand relation develops the answer. A reference relation supplies context.
  • invoke creates one user-interaction node referring to the selected node and action, then calls Complete once.
  • input embeds a bounded text, single-select, or multi-select control in the node detail grammar. It is neither navigation nor an independent invocation.
  • The product does not expose navigate relations or authoring provenance. These fields enforce graph semantics.
  • Expand paths are recursive without a fixed depth. Reference paths do not increase expansion depth.

There is no universal Go deeper button. Deeper detail exists only when the harness authors an appropriate expand action.

Authored-action lifecycle

  1. During a Complete run, the harness authors an action in draft state on a draft or reused node.
  2. The engine validates the source, authoring layer, key, kind, relation, target, ownership, visibility, and context-specific permission.
  3. The action becomes visible only when its graph version is submitted and accepted.
  4. A navigate selection reads its target locally and does not change graph state.
  5. An invoke selection creates a new node-action interaction containing the source node ID, action ID/key, optional user text, and inherited workspace binding. That new interaction is the root of the next Complete input graph.
  6. The original action remains part of its accepted snapshot. It is not consumed or converted into the new turn.
  7. Stop or failure leaves the invoked action terminal and unresolved. It does not create an accepted result layer.
  8. Retry uses the same interaction node. Only one accepted root expand action can become that interaction's canonical output.
  9. An accepted action remains immutable. A successful invoke can gain an append-only resolution that projects navigation to its accepted result.

The root output is exactly one interaction-authored expand action. The desktop follows it after acceptance. Later selections use ordinary local navigation.

Node-authored interaction input

  • An accepted input action is immutable, node-owned, and occurrence-scoped by presenting interaction, layer, and action IDs. Reuse of the same action in another accepted occurrence is a distinct attachment choice.
  • The user may answer multiple input actions across nodes. Standard controls implicitly accept the current value unless Undo restores the previous saved value. They have no separate confirmation check mark. Pending edits remain available while navigating within the workspace. Authored controls retain their selection-change and text-blur save behavior.
  • Each submitted ordinary input requires a Navigate action from its exact source Node to the returned response, like an annotation. Trusted preparation grants only this response-link operation.
  • Send saves current unbound answers, then atomically creates one root interaction and snapshots only ordinary chat inputs. Inputs explicitly connected to accepted Invokes stay outside chat and its composer. Each Invoke saves and snapshots only its connected current answers. Failed saves prevent execution and retain the edits. Values and exact occurrences are frozen before awaiting saves; later edits survive submission.
  • Send waits for an input commit still in flight, including one started when pressing Send moves focus out of the input (#521). That answer then goes with that Send.
  • If that commit fails, the Send stops. The input reports the failure, and the message stays in the composer. A commit still in flight counts toward Send being ready.
  • A failed commit stops the next Send once, even after its Node Details closes. Sending again goes without that answer. Detaching or committing that input again clears the failure.
  • Input controls are locked while a Send is in flight. A commit made while an interaction runs goes into the draft for the next Send.
  • No input action is required. An empty message is valid when at least one attachment is submitted.
  • Text values preserve authored text. Select values persist stable option keys plus their accepted labels, with multi-select keys canonically ordered. The harness receives unordered prompt/control/value snapshots without product-assigned priority.
  • Failure or stop restores the attempt's attachments to the draft unless a newer commit already owns the same occurrence. The immutable attempt cannot be retried in place; the next Send creates a new root.
  • Accepted input actions retain their authored payload in V1 conversation export even when unanswered. Accepted and terminal submitted input remains readable in compact history, safe diagnostics, and export. Import assigns fresh local identities, strips execution authority and digests, and keeps imported input read-only and inert.
  • An imported submitted input is retained only when its accepted presenting occurrence belongs to an earlier conversation turn than the consuming turn. An occurrence presented in the same turn or a later turn is dropped and recorded on the import receipt.
  • Within one consuming turn, only the first valid answer for an exact presenting interaction, layer, and action occurrence is retained. An additional answer for that occurrence is dropped and recorded with reason input_attachment_duplicate; the same occurrence may be answered in a different consuming turn. These import rejection rules are tracked by issue #312.

6.6 Artifact viewer

User goal: See what the agent built inside Relayer, without leaving the app.

Product rule: An artifact is an accepted node. Its layer says to read it in the artifact viewer.

Observable result: Opening an artifact shows it live and full screen, with notes the user can send back.

Acceptance: The viewer shows the accepted artifact and says when it changed. It never runs agent code with Relayer's authority.

Issue #684 holds the design record. Branch claude/relayer-artifact-viewer-acfefa holds the throwaway prototype and its case matrix. ADR 0014 records the architecture.

6.6.1 Artifacts in the graph

  • An artifact is a node with artifact details. A layer whose renderer is artifact holds exactly one such node.
  • The node holds everything about the content: source, kind, the part to show, starting state, screen size and fingerprint.
  • The layer only says which renderer reads its node. Two views of one artifact are two nodes in two layers.
  • The artifact node appears only in its artifact layer. Ordinary navigate actions elsewhere in the graph open that layer.
  • An artifact node may carry navigate actions and references. They appear in the graph's Node Details, never inside the viewer.
  • Draft, accepted and stopped states apply as for any layer. Users only ever open accepted artifact layers.

6.6.2 The viewer

  • Opening an artifact layer replaces the whole window with the viewer. Esc or Graph returns to the graph where the user was.
  • A slim strip at the top always shows the address or file path. Content cannot hide it or draw over it.
  • The toolbar appears when the pointer reaches that strip and hides again after about three seconds.
  • The toolbar holds Graph, the title and kind, the address, Annotate as an icon, and ⋯.
  • ⋯ › Open externally opens a URL or app in the user's browser and a file in its default app.
  • The viewer shows no node description, actions or references.

  • A video segment stops at its end until the user chooses to play the whole video.

6.6.4 Isolation

  • Each artifact node renders in its own isolated browser view, with its own storage. Nothing persists between opens.
  • Artifact content cannot reach Relayer's API, login, cookies or IPC, or another artifact's storage.
  • Popups, downloads and device permissions are refused. Camera, microphone, location and notifications are never granted.
  • A link to another site is offered in the toolbar, and one click opens it in the user's browser. The page cannot open the browser itself, and the artifact stays where it was.
  • Websites may load internet resources such as fonts. Deployed sites must use https. Plain http is allowed only for loopback addresses.
  • Local files are served from the thread folder only. Video and audio support seeking.

6.6.5 After acceptance

  • Acceptance pins a fingerprint of the file, or of every file under a site root. URLs and apps have none.
  • When the fingerprint no longer matches, the viewer shows Changed since this was accepted. It still shows the current file.
  • A file missing after acceptance shows a card saying so, with Add to chat. No agent turn starts by itself.
  • Page script errors appear as a count in the toolbar, with Add to chat. They never block viewing.

6.6.6 Web apps and the server invoke (P2)

  • An app artifact's node carries one server invoke. It names a start command, a loopback ready URL and an idle timeout.
  • Opening the viewer runs the server invoke deterministically. No model runs, and no turn or graph record is created.
  • If the ready URL answers, the viewer uses that server. Otherwise Relayer runs the command in the thread folder and waits.
  • The first run of a command in a thread asks the user for approval. Later runs reuse that approval.
  • The command runs under the thread's sandbox and permission profile.
  • On macOS, Ask and Auto threads let the command write only in the thread folder and temporary space. Elsewhere it runs only with Full access.
  • While starting, the viewer shows the command and its log. A failure shows the log, Retry and Add log to chat.
  • A server Relayer started stops after its idle timeout once no viewer shows it. The default is one hour.
  • Relayer never stops a server it did not start.

6.6.7 Starting state (P2)

  • A website or app node may seed local storage for its own origin. A web app may also seed cookies.
  • Every open clears the artifact's storage and applies the seed again, so each open starts the same way.
  • Agent guidance says seeds hold test values only. Seeds are stored in the graph and exported with it.

6.6.8 Annotations (P2)

  • Annotate opens a small panel below its icon. It lists notes already in the chat draft, each with remove.
  • The panel shows where the user is, a screenshot of the current view, and a note field. Enter adds the note.
  • Where the user is means the page, the video time, the route and scroll position, the heading or the slide.
  • Playing video and audio pause while the panel is open and resume when it closes.
  • Notes join the thread's one chat draft. The user sends them from the thread composer after leaving the viewer.
  • Sending creates one interaction that refers to the artifact node and carries every note with its screenshot.
  • Each note is an annotation on the artifact node that names its screenshot. Relayer keeps the image, and the agent opens it as a file.
  • Notes are not graph comments. Existing Comments stay private and are never sent to the agent.
  • Conversation export and shared snapshots keep each note's text and location. Exporting the screenshots themselves is a follow-up (decision 2026-10-07).

6.6.9 Office documents (P3)

  • Word, Excel and PowerPoint render in the viewer with open-source renderers. Excel shows each sheet. PowerPoint charts may draw wrongly.
  • Agent guidance says to save calculated values in spreadsheets. Totals otherwise render blank.
  • Agent guidance says to export a PDF next to any deck with charts, and to point the artifact at the PDF.
  • PowerPoint uses an MIT-licensed renderer that draws the fixture deck, its chart included (decision 2026-10-08).

6.6.10 Share and Eval

  • In a shared snapshot, a deployed https artifact plays live. Any other artifact shows a card saying where it can be viewed.
  • That card never shows a local path, folder name or loopback address.
  • Eval renders artifact layers with the same viewer. Imported conversations show the same card when files are absent.

6.6.11 Delivery

  • P1: artifact layers, integrity checks, fingerprints, agent previews, the viewer, websites, PDF, video, images, Markdown and https sites.
  • P2: web apps and the server invoke, starting state, and annotations.
  • P3: Word, Excel and PowerPoint.
  • A surface that does not know the artifact renderer shows the layer as an ordinary one-node graph.

  1. resolves cases, harness configurations, graph schema, client builds, and judge configuration at the runner boundary;
  2. uses the product app server, Rust graph server, and persistent Node harness host;
  3. creates ordinary product interactions and active harness-session context through the product API;
  4. invokes complete(inputGraph) through the Node host;
  5. runs deterministic graph checks before any model judge;
  6. runs the pinned quality judge only when deterministic checks pass;
  7. saves graph store, resolved display layer, results, scores, traces, timing, and screenshots into one immutable run directory;
  8. persists the execution and exposes Product workspace, Judge review, and Candidate trace actions in Relayer Eval;
  9. stops the temporary processes and removes the workspace unless retention was explicitly requested.

Live commands require an explicit confirmation in Relayer Eval plus an available credential reference and declared cost cap. They never run inside npm run check or the default test suite. CI may run them only in a separately authorized, budget-limited job. Closing a review window does not orphan a run: the local runner service retains status, cancellation, and the immutable partial failure record.

13.4 Judge design

Deterministic checks run first. Empty-project and project cases use the selected desktop judge contract. The former standalone six-fact structured judge is retired.

The first project suite adds one simulated-user judge. The judge opens the completed turn in the exact read-only production workspace, explores the response through visible controls, and grades what the product actually communicates. It does not substitute raw graph JSON, database records, or hidden node text for the rendered experience. Every qualitative rating is supported by screenshots captured during that review session.

Configuration comparison and blind pairwise judging are later evaluation-runner capabilities. When added, the judge model/version, prompt version, rubric version, repeat count, thresholds, and tie policy are recorded with the run. Human review in the real graph UX remains required before product promotion.

13.4.4 Coverage and completion

The review-writing tools reject unrelated evidence, unknown rubric keys, mismatched screenshot state, invalid nullability, incomplete action rankings, and missing recursive dependencies immediately.

submitReview lists missing subjects when coverage is incomplete. Expansion coverage includes every layer, node, visible action, and the overall turn.

Reference traversal processes each unique layer once and follows reference actions transitively. It does not activate inherited expand, invoke, or resolved-invoke actions.

The judge still grades those visible inherited actions in their reference context.

The final artifact preserves traces, screenshots, metadata, incremental reviews, rubric version, judge configuration, and completion coverage.

The opt-in node-input round-trip proof is separate from npm run check. A reasonable deployment-planning request exercises the fixed action matrix without naming implementation controls. It asks for a free-form deployment window, one exclusive rollout strategy, and several validation signals with a minimum of two. A live model must author the corresponding accepted text, single-select, and multi-select actions together on one decision node. The operator must commit each exactly once and Send them into a new root with provenance-exact input children. The next candidate trace must contain every exact normalized semantic input snapshot. A screenshot-grounded gate requires the rendered follow-up to visibly apply the window, strategy, and every selected signal. Deterministic real-Electron proof exercises the editable production controls and the minimum-selection error. It also covers commit, reopen, Undo, rejected persistence, detach and recommit, input-only Send, send locking, and read-only submitted history. Large-text scaling remains usable. Up to three ordinary choices must fit the details rail without horizontal discovery. Node Details fills the available pane. Opening + overlays the annotation editor without changing the detail viewport height or scroll position. The detail region scrolls independently beneath the editor. Confirmation or discard removes the overlay and reveals the covered content.

When the judge finds one material missing action, affected turn criteria and the overall presentation ceiling cannot exceed 6. Repeated material omissions or one critical omission cap them at 4. These are maximums, not assigned scores: the judge still chooses and explains the score warranted by the visible experience. Historical reviews retain their native scale when viewed alone; mixed-scale multi-turn projections normalize legacy scores proportionally before aggregation.

The simulated-user judge grades only what the product made visible. Separate deterministic graders remain authoritative for graph integrity, mutation policy, repository diff, protected-file hashes, public and hidden tests, build results, and commit history. A visually strong graph cannot compensate for broken code, and correct hidden work cannot compensate for an unusable visible response.

9.1 Relayer Eval application

Relayer Eval is a developer-only local web application launched from a checkout, with a separate local profile. It owns cases, harness configurations, judges, execution state, scores, and aggregate results.

Each case and harness execution creates ordinary product projects, threads, interactions, and accepted graph output through the Relayer app server.

Each completed execution exposes three actions:

  • Product workspace opens the accepted product thread.
  • Judge review opens the saved simulated-user evidence.
  • Candidate trace opens the portable harness trace for available turns.

The terminal owns Eval service lifetime. Closing a tab leaves evaluations running. Ctrl-C stops owned services. Startup locks the selected profile to prevent concurrent hosts. The dashboard and human review pages use separate origins and scoped capabilities. Rust credentials stay in the backend. Prime development credentials are loaded from the selected profile and imported into the secure Eval credential store. On macOS, encrypted profile persistence uses a Keychain-held master key.

Automated judges use isolated contexts in the pinned Chromium browser. They receive read-only authority and no human annotation credential. A commissioned input operator keeps its separate write authority in the backend. Browser Eval verifies the shared production workspace; Electron-specific behavior still requires desktop proof.

Deterministic host authority checks run in test/eval-web-host.test.mjs. The inference-free browser and process proof is npm run test:eval-web, after npm run build and npx playwright install chromium. It covers real product execution, review, capture, and restart. Paid judges remain opt-in.

Eval launch does not build or package an application. Developers prepare the shared runtime once and rebuild it when compiled sources or dependencies change. Dashboard, renderer, and host JavaScript edits need only reload or restart. Eval has no packaged mode or packaged-startup maintenance.

The existing npm run build refreshes shared runtime artifacts, including the root Complete output. Developers own artifact freshness and Cargo output selection, then restart Eval after rebuilding. Eval adds no preparation command or artifact-isolation guarantee. After building, npm run test:eval-compiled-runtime exercises the real recursive-Complete scenarios through the compiled root entry point.

9.2 Production-workspace review

Product workspace opens the production renderer with server-enforced read-only authority. It does not translate the graph into a second evaluation view.

The review workspace uses normal product behavior:

  • the canvas renders the exact accepted layer;
  • turn, layer, breadcrumb, Back, Forward, selection, and inspector behavior matches Relayer Desktop;
  • the sidebar contains only the selected run, harness configuration, cases, and their product threads;
  • composition and mutating actions are absent;
  • the app server rejects writes made with the review session.

9.3 Simulated-user review

A project evaluation may run several threads and turns against one pinned repository materialization. After each accepted turn, the configured simulated-user judge opens the same read-only production workspace a person reviews. It navigates visible nodes and actions and captures the screenshots it needs. It then fills the literal rubric in Section 13.4 and saves its exploration trace with the immutable run.

The judge may change only review presentation state: visible selection, navigation history, and screenshot target. It cannot send a message, invoke mutating actions, change project files, alter graph records, or modify the source run. Human reviewers can open the same execution and inspect the exact screenshots cited by each finding.

9.4 Candidate trace contract

Each available candidate trace has a versioned manifest, ordered events, achieved coverage, byte length, digest, and artifact reference. The trace excludes graph credentials and secrets.

Eval records graph HTTP operations at the product runtime boundary for every harness and case. The bounded ledger preserves response order, operation path, status, stable error codes, and sanitized graph result identities. It excludes bearer tokens, control credentials, database paths, and provider-private payloads. It remains a distinct integrity-described artifact beside the provider trace; one cannot substitute for the other.

Trace capture failure does not rewrite the product execution. It marks the execution non-promotable and preserves the explicit capture error.

Authoring-error measurement (approved 2026-10-06): Each Eval turn records authoring failures separately from timing, task outcome and graph quality. Count origin failures once; repeated attempts count separately. Infrastructure failures and ordinary reads are excluded. Failed program exits are not added to server or client error counts. Version 1 records observed server write rejections and supported JavaScript client/compiler diagnostics, including caught compiler errors. Its capture is partial: unknown methods, Python pre-transport validation, pinned or older clients, and lost diagnostic delivery are not exhaustively covered. The exact total remains unknown, including when zero errors were observed. Missing or invalid evidence is unavailable rather than zero. Measurement cannot alter candidate acceptance, judge scores or trace validity.

16.1 Product tests without paid inference

The default suite uses a fake or replay Complete implementation. It covers:

  • every visible choice and event in Agent setup, New thread, projects, Git/worktrees, thread management, settings, updates, graph navigation, context attachment, stop, retry, and recovery;
  • desktop interaction/session assembly plus Relayer input-graph and workspace-binding assembly for messages, attached context, and node actions;
  • graph-engine read/write authorization, active-interaction token checks, schema compatibility, resolved-layer reads, and migration rules;
  • node/edge/layer/action validation, recursive submission closure, atomic acceptance, historical immutability, and exact target-layer rendering;
  • secret redaction and local persistence boundaries;
  • accessibility and visual-structure assertions for all canonical mocks.

16.2 Live evaluations

Live Codex, Prime Agent, or other model runs are opt-in, metered, and never part of the default npm run check. They run through the evaluation runner and produce immutable bundles. LLM judges are versioned and calibrated against human decisions; their scores are not treated as ground truth. Simulated-user judge runs record their complete UI interaction trace and screenshot evidence so a human can audit every qualitative finding.

16.3 Human product evaluation

Human reviewers load saved results in the desktop graph UX. They judge response clarity, important details, connections, actions, and task continuation. They do not judge raw JSON or traces. Later comparisons use one case and change only the recorded harness or model configuration.

17. V1 boundary and open decisions

17.1 Included in V1

  • local profile with Codex or API-key agent login;
  • optional direct Auth0 desktop account with a pseudonymous subject and no cloud-workspace promise;
  • one OSS monorepo containing graph-engine crates, typed clients, Node harness host, harness implementations, eval runner, Rust Relayer app server, and Electron desktop packages;
  • a harness- and provider-agnostic product contract behind the Relayer Complete interface;
  • no-folder and project-backed threads;
  • non-Git folders, local Git checkout, new worktree, and fork-to-worktree;
  • graph messages, corrective or explanatory annotations through attached context, authored node actions, recursive subthreads, turn navigation, stop, retry, and local persistence;
  • bounded read-only graph search over accepted content, layers, relationships, and paths through one shared Ladybug store;
  • Rust graph core/API, opaque session-token enforcement, and TypeScript/Python graph clients;
  • persistent Node harness host, packaged codex.basic configurations, and explicit compatibility for each supported provider and harness;
  • exact empty-project Complete evaluation, followed by multi-turn, interaction, grounding, recursive-work, and hard-task capability suites;
  • Relayer Eval dashboard, read-only production-workspace review, judge evidence, and portable candidate traces;
  • Electron packages, Developer-ID-signed macOS distribution, Windows x64 distribution, and signed desktop updates.

17.2 Excluded or deferred

  • account-backed cloud sync, teams, profiles, and enterprise workspace administration. Remote hosting is excluded except for shared thread snapshots in section 8.4;
  • mandatory up-front workspace graph construction;
  • continuous background stale-node propagation;
  • self-assessment as a separate product algorithm before Complete is stable;
  • arbitrary third-party harness installation and a general-purpose pluggable harness desktop;
  • third-party conversation views, generic harness protocols, and public multi-harness conformance suites;
  • a side-by-side comparison workspace inside the production renderer;
  • Mac App Store distribution, Windows Arm, and macOS 12 or older;
  • canonical user-facing agent-activity or diagnostic-trace views.
  • a generalized public harness protocol, arbitrary harness catalog, plug-in installer, or public conformance kit;

17.3 Decisions still open

  • engine indexing and compaction implementation behind the stable read/write contract;
  • whether loopback HTTP is reachable from every supported Codex sandbox or the packaged product needs HTTP over a Unix-domain socket;
  • whether a later vector candidate source provides enough value to extend the structural search contract;
  • thresholds and calibration examples beyond the fixed first six-fact LLM-judge rubric;
  • when multiple real harness ablations justify a generalized signed configuration manifest;
  • default maximum number of Relayer-managed worktrees, whether the limit is global or per project, and the limit-reached cleanup flow;
  • exact delete-entry, graph-retention, and remove-local-data behavior;
  • exact product persistence database, export bundle, restore, and migration format. Shared snapshots use V3 for attached mutations or converted invokes, otherwise V1 when asset-free and V2 with accepted visual content. Sections 7.2B and 8.4 define these portable snapshots.

17.4 Current unproven requirements

  • Stop and retry controls do not have product proof.
  • Context attachment does not have product proof.
  • Checkout selection and new-worktree creation have deterministic production proof in docs/evidence/worktrees/README.md. Fork and worktree-cleanup flows remain unproven.
  • Rename, pin, delete-entry, move-to-project, and unsent-draft recovery do not have product proof. Archive proof is scoped to ARC-001–ARC-003.
  • API-key providers and operating-system secret storage do not have product proof.
  • Prime Agent does not have clean-install live-product proof.
  • The root package exports canonical complete(inputGraph); live app-server adoption of that exported seam does not yet have product proof.
  • The Eval promotion bundle and retention contract remain incomplete.
  • Windows signing, installation, and interactive updater canary remain blocked.

18. Product acceptance statement

V1 is acceptable only when all requirements in this section are met.

  1. The graph engine and API pass their package and end-to-end contracts.
  2. The TypeScript and Python clients pass their package and end-to-end contracts.
  3. The harness host, evaluation runner, Relayer app server, and Electron desktop pass their contracts.
  4. A developer can run empty-project.task-system.two-turn through codex.basic.
  5. The run uses one harness session and produces two explicitly submitted graphs.
  6. The run passes deterministic and judge gates.
  7. The developer can inspect both exact results in the Relayer graph UX.
  8. A local user can install a signed and notarized Relayer Desktop build.
  9. The user can configure the supported agent and start a no-folder or project thread.
  10. The thread reuses the same live harness session across turns.
  11. The user can inspect exact movable layers and use context and authored actions.
  12. Restart and update must preserve projects, threads, graph state, and settings.

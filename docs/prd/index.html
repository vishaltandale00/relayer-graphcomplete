Relayer Desktop and Relayer Harness: Product Requirements

Status: draft for product review Last updated: 2026-08-18

This document specifies two concrete product packages that live in this relayer-graphcomplete repository and ship together as one Relayer product:

  1. Relayer Desktop: the local-first desktop application that provides projects, threads, providers, persistence, Git/worktrees, the graph interface, updates, evaluation execution, and saved-result replay; and
  2. Relayer Harness: the graph engine, complete(inputGraph) implementation, Prime Agent integration, graph tools, and Relayer evaluation suites.

The repository is a monorepo: Relayer Desktop and Relayer Harness have explicit package and runtime boundaries, but V1 does not split them into separate repositories. V1 does not define a general-purpose harness desktop, arbitrary harness plug-ins, or a custom conversation-view framework. Those abstractions are deferred until the concrete Relayer product proves which seams are actually stable. Part I defines the desktop screens and ordinary user flows. Part II defines the Relayer graph engine and Complete boundary. Part III defines the Relayer eval runner, cases, and product replay. Part IV defines desktop packaging, distribution, verification, and V1 acceptance.

1. Product definition and whole-product view

The delivered product is Relayer Desktop running the pinned Relayer Harness bundled with that application release. A user connects an agent credential, creates a no-folder or project-backed chat, optionally selects a Git checkout or new worktree, sends interactions, stops or retries work, navigates accepted history, reopens persisted chats, and installs desktop updates. Each accepted Complete call persists a graph response. Relayer Desktop renders the returned layer as movable icon-title nodes, shows selected-node detail and actions in the right inspector, and lets prior nodes be navigated or attached to later messages.

A harness implementation/build can ship only when that exact recorded version has passed its required deterministic tests, live evaluations, saved-result replay, and human visual review defined in Part III.

Relayer Desktop owns the user-facing product:

  • local profile and secure credential storage;
  • projects, no-folder chats, threads, folder permissions, checkouts, and worktrees;
  • app-server lifecycle, composer shell, history navigation, stop/retry, settings, local persistence, recovery, packaging, updates, and release channels;
  • the Relayer graph canvas, force layout, parent banner, node inspector, actions, turn navigation, and accessibility behavior;
  • the local Relayer evaluation runner, immutable result catalog, report UI, and See in App handoff;
  • product capabilities for filesystem, Git, secret references, app data, deep links, and cancellation.

It does not implement agent recursion, decide graph semantics, or own Complete prompts and evaluation rubrics. It renders and interacts with graph state only through the graph engine's stable product APIs.

The GraphComplete runtime owns the graph and harness contract:

  • the Rust graph engine, local graph API, schemas, layers, actions, accepted graph state, persistence, migrations, and read/write authority;
  • typed TypeScript and Python graph clients used directly by harness code;
  • the persistent Node harness host, codex.basic, Complete, and later Prime Agent/IPython execution;
  • the evaluation runner, cases, deterministic checks, quality judge, and replay bundle.

These runtime pieces are implemented and evaluated together, but remain separate packages. The graph engine is authoritative; clients never open its database directly, the harness host does not implement graph rules, and the evaluation runner does not contain a second product or completion implementation. A later Relayer app-server integration will embed the same Rust graph core and call the same Node harness host that passed evaluation.

1.3 Stable Desktop-to-Harness contract

The canonical external boundary remains one Complete call. inputGraph is a small pointer whose root is the current user-interaction node; it is not a serialized copy of the project graph.

interface RelayerHarnessClient {
  complete(inputGraph: { interactionNode: NodeReference }): Promise<CompleteResult>;
}

type CompleteResult =
  | { status: "accepted"; interactionNode: NodeReference; display: ResolvedGraphLayer }
  | { status: "stopped" | "failed"; interactionNode: NodeReference; retryable: boolean; message?: string };

The app server creates the interaction and passes its pointer to Complete. The selected harness uses its bound graph client to construct nodes, edges, layers, and actions, then ends by calling graph.submit(interactionNode). The accepted result includes the fully resolved first layer so the desktop can display it immediately without a second request. The graph engine persists the same layer and serves later navigation. A model turn ending without submission is incomplete.

The harness choice is stored on the thread. V1 code resolves that key through a code-owned implementation map; the ordinary product does not expose a harness catalog or require users to understand harness configuration.

1.4 Deferred abstraction

V1 does not include arbitrary harness adapters, third-party conversation views, a generic agent protocol, or a public multi-harness conformance kit. The eval system may compare Relayer Harness configurations, Prime Agent versions, and model/provider choices, but every run still exercises the Relayer product contract. A general platform should be reconsidered only after the Relayer Desktop/Harness boundary has shipped and repeated implementations reveal a concrete reusable seam.

Part I — Desktop chat application

3. Agent setup and credentials

3.1 First launch

Relayer has no product account in V1. It uses one implicit local profile. First launch opens Agent setup and, after a valid configuration is saved, opens the normal New thread window. Folder and project choice are not onboarding steps.

The setup surface is one focused Agent login card. Codex and API key are presented as horizontal login-method choices, followed by the credential and model controls for the selected method. The form should not split setup into equal Harness and Agent login columns or stack alternative methods into a long vertical option list.

An Advanced disclosure below the ordinary login controls contains the harness selector and its short explanation. Prime Agent is the only enabled V1 harness, and it is preselected. Harness selection is a new-thread default: changing it never changes an existing thread. The persisted value is a stable harness identifier rather than a hard-coded UI assumption, but a first-time user does not need to understand harness architecture to connect an agent.

3.2 Login methods

Codex

  • Connect Codex starts the managed ChatGPT/Codex browser authentication flow.
  • The credential is an agent credential, not a Relayer identity.
  • Successful authentication populates compatible model choices.
  • Expired or revoked authentication returns the user to Agent setup without losing projects, threads, or graphs.

API key

  • Choosing API key reveals a provider selector.
  • Known providers can prefill their default API URL.
  • Other reveals a required provider name and API base URL.
  • The API key field is masked, supports paste, and is never written to logs, graph data, chat history, annotations, exports, or diagnostics.
  • The key is stored in the operating-system credential store. Product settings persist only a credential reference.
  • A Test connection action verifies authentication and model listing without invoking Complete.
  • The model selector is enabled only after the credential test succeeds.

3.4 Product requirements

  • AGT-001: No Relayer sign-up, sign-in, avatar, cloud-sync promise, or Sign out action appears in V1.
  • AGT-002: Agent login is the primary setup task; harness selection is available only inside a collapsed Advanced disclosure.
  • AGT-003: Prime Agent is the preselected and only enabled V1 harness; its advanced selector remains present so the persisted product contract is not designed around a permanent singleton. A harness change applies only to newly created threads.
  • AGT-004: Codex and API key are the enabled V1 login methods.
  • AGT-005: Provider-specific controls appear only after API key is chosen.
  • AGT-006: Other requires provider name and a valid HTTPS API URL, except explicitly permitted local development URLs in developer mode.
  • AGT-007: Secrets are stored through the OS credential store and are redacted from every persistence and diagnostic path.
  • AGT-008: Continue is disabled until the preselected or advanced-selected harness, credential, provider, and initial model form a valid configuration.
  • AGT-009: The composer exposes the model for the next interaction. Changing it affects that interaction and later defaults, never prior interaction records.
  • AGT-010: An existing thread cannot switch harnesses in place. To use a different harness, the user starts or forks into a new thread.

Credential-adapter integration tests use fake Codex and provider servers. One opt-in real authentication smoke is run before a signed release; it does not enter the default suite and does not execute a paid Complete call.

The first send creates one top-level user-interaction node. The thread's identity points to that root interaction node; the product does not create a separate semantic thread node for the same event.

4.2 Folder and project behavior

  • Any local folder can be a project. Git is detected capability, not a requirement.
  • Reopening an existing canonical folder reuses the project after confirmation instead of silently duplicating it.
  • Missing or revoked folder access keeps the project and history visible while prompting the user to relocate or reauthorize the folder.
  • Removing a project from Relayer never deletes the user folder or worktree.
  • A no-folder chat can be moved into an existing or newly created project when the work grows. This changes the thread's scope and sidebar placement in place; it does not create a second thread, change its root interaction ID, or discard its graph history.
  • Moving into a project affects subsequent interactions. Previously accepted turns retain the standalone scope and filesystem binding recorded when they ran.

4.3 Git-aware execution options

When the selected project is a Git repository, an execution control appears beside the folder control:

  • Local checkout: use the opened folder and its current branch.
  • New worktree: choose a base branch, create an isolated worktree, and start the thread there. V1 exposes only Local checkout and New worktree, matching the compact Codex-style decision. Base-branch, custom-location, and existing-worktree controls are deferred until a demonstrated product need. Non-Git folders do not show Git controls or empty Git status.

Forking a thread can keep its current execution location or create a new worktree. The new interaction inherits the conversation graph and project ontology while retaining its own thread-specific history.

4.4 Requirements

  • SCP-001: Send is disabled until the composer has text and a valid No folder or project scope.
  • SCP-002: No folder never receives a user folder path by implication; the stored internal scope remains standalone.
  • SCP-003: Project scope always resolves through a stable projectId; display names and paths are metadata, not identity.
  • SCP-004: Git controls appear only when Git detection succeeds.
  • SCP-005: Worktree creation errors leave the draft intact and offer retry or Local checkout.
  • SCP-006: The Complete request records the exact project, checkout/worktree, and repository state selected at send time.
  • SCP-007: New thread, fork, rename, archive, pin, delete-entry, and reopen actions are available from expected sidebar or thread menus.
  • SCP-008: Deleting a thread entry never deletes graph nodes referenced by another thread or turn.
  • SCP-009: Moving a no-folder chat into a project preserves thread and graph identity, records the scope transition, and uses the selected project only for later interactions.

5. Desktop shell, persistence, settings, and updates

5.1 Persistent shell and thread management

The left sidebar contains New thread, no-folder chats under the user-facing Chats label, projects with durable thread entries, and two compact footer icons: Settings on the left and Download update on the right when an update is available. It is a compact entry list, not a recursive graph tree. A child or subchild conversation can become a resumable sidebar entry without reproducing its full ancestry there; ancestry remains visible through graph breadcrumbs.

The header shows the current thread title, scope, and backward/forward turn controls. The composer remains the place to send, stop, and attach context. There is no separate active run dashboard.

5.2 Local persistence and recovery

Product data is local and disk-persisted:

  • profile and non-secret settings;
  • provider configuration references;
  • projects and authorized-folder metadata;
  • thread/sidebar projection;
  • user-interaction nodes, graph data, accepted snapshots, and execution status;
  • update state and schema version;
  • optional developer traces when explicitly enabled.

Persistence uses atomic writes or transactions. A crash may interrupt an in-progress Complete call, but it must not corrupt the last accepted graph. On reopen, accepted turns render immediately; an interrupted interaction is marked stopped or failed and retryable. Recovery is a reliability requirement, not a primary product concept or prominent settings category.

5.3 Settings information architecture

Normal settings contain:

  • Agent: harness, login method, provider, model, reconnect, replace API key.
  • Projects and storage: local data location, export, and remove-local-data actions.
  • Git: default execution choice, worktree location, and the maximum number of worktrees Relayer may create; visible only when meaningful.
  • Updates: current version, channel, automatic download preference, and Check for updates.
  • Appearance and behavior: theme and ordinary desktop preferences.

Signed desktop updates are essential V1 distribution infrastructure.

6.2 One cumulative graph and four records

Relayer product storage owns projects and threads. Graph core does not create project records, thread records, project graphs, thread graphs, graph spaces, or a separate interaction graph. It stores the product-owned positive-integer projectId and threadId on graph records as provenance. Threads with the same project ID read the same accepted graph records. A no-project thread stores projectId = null and reads only records carrying its own thread ID, so standalone threads never share graph records.

Every user turn is represented by one canonical user-interaction graph node. That node's NodeReference is also the product interaction identity after integration; no second interactionNodeId is synthesized. The host supplies project/thread IDs when it asks graph core to create this node. A graph capability stores only the node reference. On every graph request, the engine calls GraphDatabase::writer_for_subgraph(node) and derives read visibility plus draft-write authority from the persisted node.

type NodeReference = number; // positive SQLite integer assigned after successful submission
type EdgeReference = number;
type LayerReference = number;
type ActionReference = number;

type GraphNode = {
  ref?: NodeReference;
  icon: string;
  title: string;
  detail: string; // Markdown/HTML-compatible product detail
};

type GraphEdge = {
  ref: EdgeReference;
  endpoints: readonly [NodeReference, NodeReference]; // undirected
};

type GraphLayer = {
  ref: LayerReference;
  nodes: NodeReference[];
  edges: EdgeReference[]; // exact visible connections, never inferred
};

type NodeAction =
  | { ref: ActionReference; source: NodeReference; kind: "navigate"; label: string; targetLayer: LayerReference }
  | { ref: ActionReference; source: NodeReference; kind: "invoke"; label: string; interactionText?: string };

A layer packages the exact node references and exact edge references rendered together. A navigate action always opens a layer, even when that layer contains only one node. Actions are separate graph records associated with a source node; adding an action does not require resubmitting the node.

6.3 Agent-facing TypeScript and Python client

interface GraphClient {
  getNode(ref: NodeReference): Promise<GraphNode>;
  getNeighbors(ref: NodeReference): Promise<GraphNode[]>;

  submitNode(node: GraphNode): Promise<NodeReference>;
  createEdge(left: GraphNode | NodeReference, right: GraphNode | NodeReference): Promise<EdgeReference>;
  createEdges(pairs: ReadonlyArray<readonly [GraphNode | NodeReference, GraphNode | NodeReference]>): Promise<EdgeReference[]>;
  submitLayer(layer: GraphLayer): Promise<LayerReference>;
  addAction(source: GraphNode | NodeReference, action: NodeAction): Promise<ActionReference>;

  submit(interactionNode: NodeReference): Promise<ResolvedGraphLayer>;
}

The clients are object-oriented because models are better at constructing and repairing nodes and layers than remembering large collections of raw IDs. A local node object receives its stable reference after its first successful submitNode. Resubmitting that same local object updates its current draft rather than creating a duplicate. A rejected edit preserves the last valid draft and returns a field-specific error so the harness can repair and resubmit it.

createEdge accepts node objects or references. Creating an edge from a new node to an accepted historical node does not resubmit or modify the historical node. Adding an accepted node to a new layer also does not modify it. Accepted historical records are immutable; a changed explanation is represented by a new node connected to the old node.

Error responses contain a stable code, object path, and natural-language repair message. The message is part of the agent contract: it should tell the model what failed and what operation can correct it without requiring the engine to make semantic judgments.

6.5 Recursive completion submission

graph.submit(interactionNode) is the deterministic completion boundary. Starting from the interaction's newly authored response navigate action, the engine traverses the target layer, its exact nodes and edges, and any navigate actions on those nodes. It validates the reachable closure with a visited set, atomically accepts the reachable new drafts, and leaves unrelated drafts unaccepted.

The accepted return value is a ResolvedGraphLayer containing full node objects, exact visible edges, and node actions for the root layer. This is the immediate display payload returned by Complete. The persisted layer reference remains the source for later navigation and reload.

7.2 Persistent Node harness host

The Node harness host is a long-lived child process of the evaluator or Relayer app server. It resolves a small code-owned implementation map and lazily constructs one harness object per thread:

const harnessImplementations: Record<string, HarnessFactory> = {
  "codex.basic": createBasicCodexHarness,
  "prime-agent": createPrimeAgentHarness,
};

The thread stores a copy of its selected named harness configuration. The configuration's implementation field selects a factory from the map; the host does not interpret the implementation-specific settings object. The host keeps the same JavaScript harness object and underlying provider session alive across turns. Factories may initialize asynchronously. If the Node process or provider session expires, trusted control code first registers a fresh graph capability, then the host recreates the object from stored configuration and opaque provider resume state. Continuous conversation must not rediscover, reload, or start a brand-new Codex conversation on every Complete call.

The Relayer app server will own one-active-root-completion coordination for a thread. The Node host owns the live JavaScript object, serializes construction and Complete calls on that object, forwards cancellation through an AbortSignal, and disposes live harnesses during shutdown; different thread harness objects may run concurrently. Prime Agent remains the owner of recursive child-agent scheduling inside a completion.

7.3 Minimal harness configuration

Each YAML file has a unique machine-readable name, selects an implementation type and version, and carries implementation-owned settings. The host validates only the common envelope. Each implementation validates its own settings, so a later Prime Agent harness can add model policy, recursion, review, and budget settings without changing host types.

schemaVersion: 1
name: codex-basic
implementation: codex.basic
implementationVersion: 1
settings:
  sandboxMode: workspace-write
  approvalPolicy: never
  networkAccessEnabled: true
  skipGitRepoCheck: true

The implementation registry and configuration catalog solve different problems: the registry says which code can run, while the catalog says which named production setups users and evaluations can select. Many configurations are expected to select the same implementation with different settings; only configuration names must be unique. Duplicate names fail catalog loading. A thread is pinned to the full copied configuration, not merely to an implementation type.

8. Interaction, response, and graph-memory contract

8.1 Messages and multiple turns

A message creates one interaction node, connects any selected prior state to it, and makes one Complete call. On acceptance, the engine records the run's output navigate action and response layer under that interaction. Later interaction nodes connect into the existing conversation graph and may refer to any prior node. The thread graph is the V1 conversation memory; V1 does not maintain a separate continuously updated summary.

If a later turn needs a stale explanation, the harness creates a new node and connects it to the accepted historical node. It does not rewrite accepted history. Otherwise the old node remains unchanged. Broader recursive freshness propagation is deferred.

8.2 Add as context

The permanent inline + action exists on every selectable node. It opens an optional annotation field in the inspector. After attachment:

  • the composer shows one compact graph annotation with a count;
  • a compact attachment strip appears directly above the chat box, following the familiar Codex attachment placement;
  • hover or click on that strip reveals the attached node icons;
  • selecting an icon shows the user's annotation for that node;
  • attachments persist with the draft, survive navigation, and clear only after durable send or explicit removal;
  • the next interaction node receives typed attachment edges carrying the selected node IDs and annotations.

Adding context alone does not invoke Complete.

V1 has no separate feedback interaction. When a user wants to correct, question, or expand a node, they press +, attach that node with an optional note such as “this claim is wrong,” and send an ordinary message. The note is stored on the attachment edge; the interaction remains kind = "message".

8.3 Authored node actions

Every node action except + is authored by the harness on that node. Authored actions appear inline first; the universal attach-context + is the final control in the row. An action declares:

type NodeAction = {
  id: string;
  actionKey: string;
  sourceNodeId: string;
  label: string;
  mode: "navigate" | "invoke";
  targetLayerId?: string; // required for navigate; a layer may contain one node
  interactionTemplate?: {
    kind: "message" | "node-action";
    text?: string;
  };
};
  • navigate opens an already submitted layer without Complete. A one-node destination is still represented as a layer.
  • invoke creates one user-interaction node referring to the selected node and action, then calls Complete once.
  • The accepted response becomes a child subgraph/subthread and is enterable from the parent through a navigate action and from its durable sidebar entry.
  • Subthreads are recursive without a fixed depth.

There is no universal Go deeper button. Deeper work exists only when the harness authors an appropriate invoking action.

Authored-action lifecycle

  1. During a Complete run, the harness authors an action in draft state on a draft or reused node.
  2. The engine validates that the source exists, actionKey is unique on that node revision, the mode is supported, and any navigate target exists in the submitted graph version.
  3. The action becomes visible only when its graph version is submitted and accepted.
  4. A navigate selection reads its target locally and does not change graph state.
  5. An invoke selection creates a new node-action interaction containing the source node ID, action ID/key, optional user text, and inherited workspace binding. That new interaction is the root of the next Complete input graph.
  6. The original action remains part of its accepted snapshot. It is not consumed or converted into the new turn.
  7. Stop or failure leaves the invoked interaction retryable and does not create an accepted child layer.
  8. Retry uses the same interaction node. Only one accepted response navigate action may become the canonical output for that interaction.
  9. If a later graph revision removes or replaces an action, old accepted snapshots retain the old action; the current snapshot may mark it unavailable rather than silently redirecting it.

The output navigate action created for a successful Complete run follows the same persisted action schema. It is automatically followed once by the desktop after acceptance; later selections are ordinary local navigation.

8.4 Display and navigation

  • The response view contains the first layer of the accepted subgraph, including edges among those response nodes.
  • Edges are visually undirected.
  • The interaction/parent node is not repeated inside its child layer. It appears in a centered breadcrumb above the canvas with icon and title.
  • Clicking a breadcrumb segment navigates to that node's layer locally.
  • Nodes are movable icon-title objects with force/gravity behavior.
  • Clicking a node opens its authored details and actions in the right inspector.
  • Previous and next arrows move across accepted turn snapshots without Complete.
  • The renderer shows the immutable accepted snapshot for that turn even if later turns update shared nodes.

Part III — Evaluation and product replay

9. Exact basic Complete evaluation

The first evaluation is one fixed, two-interaction case named empty-project.task-system.two-turn. It proves the smallest real conversation path through the Rust graph engine, typed client, persistent Node harness host, Codex session, Complete boundary, deterministic evaluator, quality judge, and product renderer. The second interaction receives a new canonical interaction node and capability token while reusing the same harness object and provider thread. It deliberately has no existing codebase, grounding requirement, graph search, or subagent dependency.

9.1 Initial state and exact input

The runner creates a temporary empty folder and isolated graph database, supplies synthetic positive project/thread IDs, selects the codex-basic configuration (which resolves codex.basic), and asks graph core to create two canonical user-interaction nodes in the same thread. It does not start or imitate the Relayer app server. The exact messages are:

“A task system has an incoming queue, two workers, and a results store. Explain how a task moves through the system and what happens when both workers are busy.”
“Follow up in the same thread: explain the task flow again, emphasizing what happens while both workers are busy and immediately after one worker finishes.”

The expected answer facts are declared in the case rather than hidden in harness code: tasks enter the queue; an available worker claims a task; at most two tasks are active; additional tasks wait; a completed task is written to the result store; and a freed worker claims the next queued task.

9.2 Exact runner sequence

  1. Start the standalone Rust graph server with an isolated database and wait for health.
  2. Supply synthetic product-owned project/thread IDs, ask graph core to create the first canonical interaction node, create the active harness session, and issue an opaque graph token bound to that node.
  3. Load the named harness configuration, start the Node harness host, and resolve its codex.basic implementation.
  4. Call complete({ interactionNode }); Codex constructs the response using the TypeScript graph client.
  5. Require Codex to submit nodes, undirected edges, a layer, the interaction's response navigate action, and finally graph.submit(interactionNode).
  6. Receive the first resolved root layer and run its deterministic checks.
  7. Create the second interaction in the same thread, issue a distinct capability, re-register the session, and verify the host adopts the new capability without constructing another harness object.
  8. Call Complete for the second interaction and run the same deterministic checks. The opt-in live path runs an independent structured Codex judge for each accepted turn.
  9. Save the accepted graph records, resolved display payload, checks, judge result, timing, harness key/version, and trace reference in one immutable result bundle.
  10. Load that bundle into the existing force-graph product renderer for human inspection.

9.3 Deterministic acceptance checks

The first gate uses no model judgment. All checks must pass:

  • Complete returned accepted only after graph.submit(interactionNode) succeeded;
  • both Complete outputs and response actions belong to their requested interaction nodes;
  • the second interaction uses a distinct capability token and node ID while the harness factory is called exactly once;
  • the interaction has exactly one accepted response navigate action;
  • that action targets the returned submitted root layer;
  • the layer contains between one and eight submitted nodes;
  • every visible node has a non-empty icon, title, and detail;
  • every layer edge is undirected, non-self, unique, and has both endpoints in the layer;
  • the layer is connected when it contains more than one node;
  • the resolved display payload contains exactly the layer's nodes, edges, and actions;
  • the response action, layer, every resolved node, every resolved edge, and every resolved action are explicitly accepted;
  • no unrelated or rejected draft is reachable from the accepted response;
  • the saved result can be read back and rendered without consulting harness-private state.

Local keys used by Codex while constructing one layer are temporary builder references, not persisted semantic identities and not an evaluation requirement.

9.4 First quality-judge gate

For each turn, the independent judge receives only that user message, six declared facts, and the visible resolved layer. It does not receive the candidate harness name, private Codex conversation, token, database, or expected graph topology.

The structured judge lists the fact IDs clearly present, whether the graph connections are useful, whether the details are useful, and any problems. A turn passes only when all six fact IDs are present, both usefulness booleans are true, and the problem list is empty.

9.5 Required saved visual proof

A passing JSON result is insufficient. The current pre-app-server evaluator saves an index.html beside result.json; previous/next arrows select either accepted turn, and each view shows its exact layer and movable nodes and edges. Desktop See in App, the right-side product inspector, and read-only evaluation threads remain app-server integration requirements. This separates current visual proof from the later claim that the result is running inside the product.

9.6 Next evaluations after the first slice

The current case verifies two interactions, capability rotation, one harness construction, and the accepted output contract for both turns. The next memory case must additionally require the second interaction to use prior accepted graph state. Later capability cases add context attachments, invoke and navigate actions, repository grounding, graph reuse, recursive Prime Agent work, and harder tasks.

10.3 Runner execution

Local commands are standardized target interfaces:

eval:web opens the Relayer evaluation runner shown in Mock 10. The first slice needs only case, harness implementation, candidate model, judge, live progress, final checks, and See in App. The web UI and CLI call the same runner service and produce the same bundle; the UI is not a separate evaluation implementation.

For each case the runner:

  1. resolves the case, harness implementation, graph schema, client builds, model, and judge versions;
  2. starts an isolated Rust graph server and persistent Node harness host;
  3. creates the same interaction and active harness-session context the product will create;
  4. invokes complete(inputGraph) through the Node host;
  5. runs deterministic graph checks before any model judge;
  6. runs the pinned quality judge only when deterministic checks pass;
  7. saves graph store, resolved display layer, results, scores, traces, timing, and screenshots into one immutable run directory;
  8. prints the run ID, summary, local report URL, and See in App deep link;
  9. stops the temporary processes and removes the workspace unless retention was explicitly requested.

Live commands require an explicit confirmation in the web runner or command flag plus an available credential reference and declared cost cap. They never run inside npm run check or the default test suite. CI may run them only in a separately authorized, budget-limited job. Closing the web page does not orphan a run: the local runner service retains status, cancellation, and the immutable partial failure record.

10.4 Judge design

Deterministic checks always run first. The first empty-project case then uses only the six-fact structured judge defined in Section 9.4. It does not require an operator agent, pairwise comparison, grounding rubric, repeat policy, or promotion threshold.

Later capability suites add the dimensions they actually exercise: conversation memory, node reuse, attachments, authored actions, repository grounding, topology, and operator task success. Each score cites visible node references and a short rationale. Critical failures remain separate booleans rather than averages hidden by other scores.

Configuration comparison and blind pairwise judging are later evaluation-runner capabilities. When added, the judge model/version, prompt version, rubric version, repeat count, thresholds, and tie policy are recorded with the run. Human review in the real graph UX remains required before product promotion.

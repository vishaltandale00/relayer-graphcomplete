This PRD specifies two product packages. Both packages are in the relayer-graphcomplete repository. They ship together as one Relayer product.

  1. Relayer Desktop is the local application. It provides projects, threads, providers, persistence, Git worktrees, the graph interface, updates, evaluations, and saved-result replay.
  2. Relayer Harness contains the graph engine, complete(inputGraph), harness host, supported implementations, graph tools, and evaluation suites.

The repository is a monorepo. Relayer Desktop and Relayer Harness have separate package and runtime boundaries. V1 does not put them in separate repositories.

V1 does not include a general harness desktop, arbitrary harness plug-ins, or a custom conversation-view framework. These items are deferred. The Relayer product must first show that a reusable interface is stable.

The Product capabilities come first. Contracts follow the product behavior. Evidence and acceptance appear last.

1. Product model and scope

The delivered product is Relayer Desktop with its pinned Relayer Harness. A user connects an agent credential and creates a thread. The thread can use no folder or a project. For a Git project, the user can select the local checkout or a new worktree.

Relayer has a harness- and provider-agnostic product contract. Product workflows use stable catalog identifiers and the same Complete boundary. A supported harness or provider still requires an explicit adapter, declared compatibility, tests, and release inclusion.

The user sends interactions and can stop or retry the work. The user can navigate accepted history and reopen saved threads. The user can also install desktop updates.

Each accepted Complete call saves a graph response. Relayer Desktop shows the returned layer as movable nodes. Each node has an icon and a title. The right inspector shows the selected node details and actions. The user can navigate to prior nodes or attach them to a later message.

A harness build can ship only after all required checks pass. These checks include deterministic tests, live evaluations, saved-result replay, and human visual review.

Relayer Desktop owns the user-facing product:

  • local profile and secure credential storage;
  • projects, no-folder chats, threads, folder permissions, checkouts, and worktrees;
  • app-server lifecycle, composer shell, history navigation, stop/retry, settings, local persistence, recovery, packaging, updates, and release channels;
  • the Relayer graph canvas, force layout, parent banner, node inspector, actions, turn navigation, and accessibility behavior;
  • the Relayer Eval dashboard, production-workspace review windows, immutable judge evidence, and portable candidate traces;
  • product capabilities for filesystem, Git, secret references, app data, and cancellation.

It does not implement agent recursion, decide graph semantics, or own Complete prompts and evaluation rubrics. It renders and interacts with graph state only through the graph engine's stable product APIs.

The GraphComplete runtime owns the graph and harness contract:

  • the Rust graph engine, local graph API, schemas, layers, actions, accepted graph state, persistence, migrations, and read/write authority;
  • typed TypeScript and Python graph clients used directly by harness code;
  • the persistent Node harness host, Complete, supported harness implementations, and provider adapters;
  • the evaluation runner, cases, deterministic checks, quality judge, and replay bundle.

These runtime components are implemented and evaluated together. They remain separate packages. The graph engine is authoritative. Clients must not open its database directly. The harness host must not implement graph rules. The evaluation runner must not contain a second product or Complete implementation.

The Rust app server creates product interactions and calls the same persistent Node harness host used by evaluation. It persists the accepted result and serves it to the renderer.

1.4 Relayer Desktop and Relayer Harness interface

The canonical external boundary is one Complete call. inputGraph is a small pointer. Its root is one already-prepared canonical user-interaction node. It is not a serialized copy of the project graph. Human-root product code prepares that interaction from the user event. Trusted recursive adapter code prepares or exactly recovers an agent child from one immutable published invoke occurrence. Both paths then enter the same Complete module. Model-authored code cannot substitute an arbitrary interaction-shaped node or mint child authority.

The root package exports this boundary and a process-owned configuration seam for injecting its trusted completion runtime. The Rust app server reaches the same executable seam through the persistent HarnessHost.

interface RelayerHarnessClient {
  complete(inputGraph: { interactionNode: NodeReference }): CompletionHandle;
}

interface CompletionHandle {
  readonly completionId: GraphId;
  readonly current: CompletionCurrent;
  readonly result: Promise<ResolvedGraphLayer>;
}

interface CompletionCurrent {
  snapshot(): Promise<CompletionCurrentSnapshot>;
}

interface CompletionTerminalError extends Error {
  readonly completionId: GraphId;
  readonly lifecycle: "stopped" | "failed";
  readonly current: CompletionCurrentSnapshot;
  readonly reason: string;
}

Complete returns one handle after trusted preparation establishes or recovers the canonical completion identity.

Preparation is a separate step, and it is the authority step. Agent code publishes an accepted invoke action, calls prepareComplete(action), then calls Complete.

complete(inputGraph) establishes no identity of its own. It requires an already-prepared interactionNode and rejects anything else.

Server-side capability derives from the published invoke occurrence. Exact-retry recovery keys off that same occurrence.

current observes the durable GraphComplete pointer. result resolves only from GraphComplete succeeded state and its canonical final layer.

A model turn or provider process ending does not resolve it. Stopped and failed completions retain their last current and reject result with a structured terminal error. They never fabricate a final layer.

A never-settling promise is not the contract. An awaiting agent must be able to observe child termination.

The parent's own invoke action stays unresolved and navigable to the child's retained current. An unresolved invoke never means an unsettled handle.

An agent may stop a completion whose invocation names it as the direct source. Grandchildren, siblings, and human or product callers may not.

handle.stop(reason) is that agent-only control. The stopped child retains its current and reports stopped.

Observation is delivered as current-pointer revisions only. There is no token streaming, no partial-layer publication, and no additional event kind.

An awaiting agent performs no repeated polling. The server holds one observation open and answers when the awaited completion advances, filtered to that caller's grant.

Restart never reattaches. Interrupted active completions fail safely with application_restart and keep their retained current.

No provider is asked whether its execution survived. Complete is never re-called as crash recovery for an already-started execution.

The app server creates the human-root interaction and passes its pointer to Complete. A supported recursive provider adapter derives the prepared pointer from the invoking completion and exact published invoke occurrence. It then passes that same pointer to Complete. The selected harness uses its bound graph client to construct nodes, edges, layers, and actions, then returns with current.return(layer) or the compatible graph.submit(interactionNode). The accepted result includes the fully resolved first layer so the desktop can display it immediately without a second request. The graph engine persists the same layer and serves later navigation. A model turn ending without Return is failure, never success.

The product stores one named harness on the thread. Model is the primary composer choice. Advanced shows compatible harness configurations before thread creation. The pinned harness becomes read-only after creation.

The selected harness owns model execution and provider-session reuse. Each explicitly supported recursive adapter, including Codex and Prime Agent, owns its provider-native child launch or binding, concurrency, waiting, messaging, and session behavior. GraphComplete, Relayer product, and the harness host do not add a recursive runnable queue, automatic parent wakeup, or incorporation policy. Provider adapters own authentication and model discovery. Relayer product records do not expose raw credentials, provider flags, runtime sessions, or implementation-specific recursion policy.

1.5 Items not in V1

V1 does not include arbitrary harness adapters, third-party conversation views, a generic agent protocol, or a public multi-harness conformance kit. Eval may compare supported harness, provider, and model configurations, but every run still exercises the Relayer product contract. A general platform should be reconsidered only after repeated implementations reveal a concrete reusable seam.

2.1 First launch

Relayer uses one implicit local profile. First launch opens Agent setup and, after a valid configuration is saved, opens the normal New thread window. An optional Relayer account offer may appear only after that local workspace is usable. Folder, project, and account choice are not blocking onboarding steps.

The setup surface is one focused Agent login card. Codex and API key are presented as horizontal login-method choices, followed by the credential and model controls for the selected method. The form should not split setup into equal Harness and Agent login columns or stack alternative methods into a long vertical option list.

Agent setup does not require a harness choice. After connection, the New Thread composer presents Model as the primary execution control. Its Advanced tab contains compatible harness configurations.

A successful provider connection with at least one execution-eligible model creates one product-managed, provider-scoped model family before setup completes. First launch selects the unique valid provider, family, model, and default harness route atomically; it does not require custom-family construction. Product policy admits only reviewed synchronous text or agent models and fails closed for unknown capabilities. It applies a versioned provider preference before provider order and caps the managed family at five models. OpenRouter policy version 1 is the explicit three-model general-agent roster deepseek/deepseek-v4-pro-0813, qwen/qwen3.8-max, and z-ai/glm-5.3, in that order. Vercel AI Gateway policy version 1 provides the equivalent roster using its catalog identities: deepseek/deepseek-v4-pro-0813, alibaba/qwen3.8-max, and zai/glm-5.3. Both policies omit missing or unavailable entries rather than falling through to arbitrary catalog order.

Adding a provider through Settings applies the same managed-family policy. It preserves the existing default provider, family, model, harness, open composer draft, and existing thread bindings. Refresh reconciles only the refreshed provider's managed family. Custom families are never rewritten by managed-family reconciliation. A connected provider with zero eligible models remains in the typed provider_no_eligible_execution_models recovery state and cannot silently populate an unsafe family. Its provider card and first-run setup expose an exact-provider Refresh models and set up defaults action. Refresh reruns managed-family derivation for that same provider and advances automatically when a valid default route becomes available.

The packaged application includes codex-basic as its Codex product harness. codex-basic-high remains available only to internal Eval and code workflows. Prime Agent configurations remain development targets until a clean installation can load the upstream package.

2.2 Login methods

Codex

  • Connect Codex starts the managed ChatGPT/Codex browser authentication flow.
  • The credential is an agent credential, not a Relayer identity.
  • Successful authentication populates compatible model choices.
  • Expired or revoked authentication returns the user to Agent setup without losing projects, threads, or graphs.

API key

  • Choosing API key reveals a provider selector.
  • Known providers can prefill their default API URL.
  • Other reveals a required provider name and API base URL.
  • The API key field is masked, supports paste, and is never written to logs, graph data, chat history, annotations, exports, or diagnostics.
  • The key is stored in the operating-system credential store. Product settings persist only a credential reference.
  • A Test connection action verifies authentication and model listing without invoking Complete.
  • The model selector is enabled only after the credential test succeeds.

2.3 Model and harness selection

  • The composer places Model immediately before Submit.
  • The Model tab selects one enabled family and one available compatible model.
  • The Advanced tab selects one compatible harness before thread creation.
  • The thread pins that harness. Follow-up interactions cannot change it.
  • A follow-up may select another compatible model. Prior interaction receipts remain unchanged.
  • Harnesses Settings lists only harnesses usable now. Provider and model diagnostics remain in their owning Settings surfaces.
  • Every connected provider with eligible execution models exposes its product-managed family in both first-run onboarding and Settings without a separate family-construction step.
  • Existing UI-authored harness rule overrides reset once to catalog defaults when their editor is removed.

2.5 Authenticated error reporting

Electron main is the only Sentry authority. Renderer and child processes submit typed records through generation-bound local capabilities.

Only a verified account generation enables admission. Every other account state creates no request or queue record.

Main derives one stable identifier with SHA-256("graphcomplete-sentry-user-v1\0" || UTF-8(Auth0 sub)). Callers cannot supply identity or transport configuration.

  • V1 reports only unhandled process crashes, supervised-child startup failures, and supervised-child unexpected exits.
  • Handled operation failures, validation, denials, cancellations, retries, disconnections, warnings, information, and success never report.
  • Accepted JavaScript frames use application-relative module names. Each event keeps at most 32 frames and 256 characters per module name.
  • Rust frames name only approved workspace crates and modules. Absolute paths and third-party frames are rejected.
  • Every module name must match the exact packaged-module inventory. Valid-looking invented names are rejected.
  • Approved fields are stable failure code, code-owned message, frames, component, operation, release, environment, OS, architecture, and pseudonymous identity.
  • Prompts, graph or model content, paths, commands, environment data, credentials, requests, URLs, logs, and raw errors are forbidden.
  • Breadcrumbs, attachments, replay, tracing, profiling, performance events, default PII, and automatic request context remain disabled.

The encrypted queue holds at most 32 records and 256 KiB. Records expire after seven days, and overflow evicts the oldest record.

Any corrupt queue is deleted. Retry requires revalidation of the same Auth0 subject and never creates recursive telemetry.

Logout or account replacement disables admission and deletes the old queue before account presentation changes.

Release identity comes only from immutable sealed package metadata. Electron main supplies the Sentry environment from its validated current update channel.

The versioned shared privacy corpus covers every process seam and forbidden field. npm run evidence:telemetry runs its deterministic portfolio.

Live Auth0, packaged storage, system-browser, upload, and symbolication proof runs only for Preview or Stable release candidates.

Each target proves only its native platform: macOS Apple Silicon, macOS Intel, or Windows x64. Missing target evidence remains indeterminate.

10.2 Desktop application updates

11.2 One cumulative graph and four records

Relayer product storage owns projects and threads. Graph core does not create project records, thread records, project graphs, thread graphs, graph spaces, or a separate interaction graph. It stores the product-owned positive-integer projectId and threadId on graph records as provenance. Threads with the same project ID read the same accepted graph records. A no-project thread stores projectId = null and reads only records carrying its own thread ID, so standalone threads never share graph records.

Every user turn is represented by one canonical user-interaction graph node. That node's NodeReference is also the product interaction identity after integration; no second interactionNodeId is synthesized. The host supplies project/thread IDs when it asks graph core to create this node. A graph capability stores only the node reference. On every graph request, the engine calls GraphDatabase::writer_for_subgraph(node) and derives read visibility plus draft-write authority from the persisted node.

The clients are object-oriented because models are better at constructing and repairing nodes and layers than remembering large collections of raw IDs. A local node object receives its stable reference after its first successful submitNode. Resubmitting that same local object updates its current draft rather than creating a duplicate. A rejected edit preserves the last valid draft and returns a field-specific error so the harness can repair and resubmit it.

createEdge accepts node objects or references. Creating an edge from a new node to an accepted historical node does not resubmit or modify the historical node. Adding an accepted node to a new layer also does not modify it. Accepted historical records are immutable; a changed explanation is represented by a new node connected to the old node.

11.5 Recursive completion submission

graph.submit(interactionNode) is the deterministic completion boundary. It derives exactly one interaction-authored root expand action.

The engine traverses only current-interaction actions. Expand paths must be acyclic. Reference paths can branch, share destinations, or cycle.

A visited set terminates reference traversal. Accepted reference targets are immutable boundaries. The engine validates visibility and authority without reaccepting their history.

The engine rejects unreachable current-interaction layers. One atomic operation accepts the valid reachable drafts. A focused flat root remains valid.

The accepted return value is a ResolvedGraphLayer containing full node objects, exact visible edges, and node actions for the root layer. This is the immediate display payload returned by Complete. The persisted layer reference remains the source for later navigation and reload.

  • The public language is a bounded read-only GQL/Cypher-shaped profile, not full Cypher or ISO GQL.
  • V1 supports whole-target scans plus fixed one-hop and two-hop patterns.
  • Content, layers, connections, membership, expansions, and references form one searchable supergraph.
  • Drafts, interaction.context, and unresolved invokes never enter the searchable topology.
  • Queries return typed scalar, graph, list, record, and path values with deterministic ordering.
  • The default result cap is five rows. The hard cap is eight rows and 16 KiB.
  • Rows are never partially truncated. A single oversized row returns a typed error.
  • Output limits do not replace traversal, expansion, intermediate-row, time, or cancellation budgets.
  • Incompatible Ladybug stores rebuild from SQLite before an atomic validated swap.
  • V1 uses pinned official Ladybug components and narrow hooks. It does not require a permanent fork.
  • Vector retrieval and making Ladybug canonical for writes are deferred.

The versioned graph-query contract freezes grammar, values, topology, limits, errors, and compatibility.

The thread stores a copy of its selected named harness configuration. The configuration's implementation field selects a factory from the map. The Relayer app server owns one-active-human-root-completion coordination for a thread. The Node host owns the live JavaScript object and a completion registry keyed by canonical completion identity. 4.3 Personal presentation profile

Relayer owns one hidden, versioned personal presentation graph that guides how supported harnesses author response graphs. This guidance is a preference, not a mandatory output schema. Explicit user instructions take precedence. Graph integrity remains deterministic, and a flat accepted answer remains valid.

Each version is an ordinary immutable accepted GraphComplete completion in one dedicated product-owned profile thread. Neutral V0 contains no renderable preference. Active V1 contains exactly two presentation-preference nodes with authored layout and their ordinary graph relationship:

  • Decision-useful center: foreground the conclusion or current status, the reasoning that materially affects it, and the most important tradeoffs or limitations.
  • Adaptive progressive disclosure: keep information central when it is necessary for immediate understanding. Use graph actions when supporting evidence, implementation detail, or secondary context materially improves understanding or helps the user proceed. Do not add branches that repeat or decorate the central explanation.

Published V2 is a third ordinary immutable completion in the same hidden profile thread; V1 remains active until a separate reviewed activation. V2 does not reuse or mutate V1 graph records. Its one required root layer owns self-contained versions of the two V1 concepts plus a third presentation-preference node:

  • Visible working state: for work that will not finish immediately, prefer establishing a useful current early. Prefer advancing it often enough for the user to follow and steer the work. Exercise judgment so updates remain useful rather than noisy. Then return an integrated final response. Use separate semantic work scopes when available and useful, but preserve visible progress when all work remains inside one completion. Do not expose private scratch reasoning or create decorative progress updates.

Decision-useful center is the V2 root layer's semantic hub. Ordinary undirected edges connect it to Adaptive progressive disclosure and Visible working state. Its authored triangular layout places the hub above the two related preferences. V2 has no nested preference layer.

Interaction creation atomically pins one published, non-retired version through a control-owned attachment. The attachment references the accepted profile completion rather than copying it. Preparation, retry, recovery, and resumed provider sessions reuse the stored pin. Changing the active version affects only interactions created afterward. Invalid, missing, retired, mismatched, duplicate, or cross-scope versions fail before provider execution. Historical interactions without an attachment remain readable.

An invoke-created semantic child atomically copies the source interaction's exact pinned version into its own control-owned attachment. It does not resolve the version active when the child is created. Retry and restart therefore preserve one personalization graph throughout a semantic task tree even if product policy changes while the root is running.

The harness deterministically renders the pinned graph after generic GraphComplete guidance and before the task input. The root and provider-native children that can author graph content receive the same rendered guidance; unrelated delegates do not. Model and provider capabilities cannot create, replace, remove, or mutate the attachment or published preference graph.

When current advancement is supported, the graph can be a useful working surface before terminal acceptance. An advance publishes a validated durable layer as current without completing the interaction. Later material changes may advance another immutable revision. Return establishes the final accepted layer. These presentations contain decision-useful work state, not token streaming, tool-by-tool narration, or private chain-of-thought. Semantic children are optional and do not define current-pointer progress.

The attachment is not a response edge, action, context occurrence, or accepted response record. It never enters completion closure, root-action counting, graph navigation, visible topology, Node Details, ordinary history, or conversation export. 7.2 Authored node actions

Every node action except + is authored by the harness on that node. Authored actions appear inline first; the universal attach-context + is the final control in the row. An action declares:

type NodeAction = {
  id: string;
  actionKey: string;
  sourceNodeId: string;
  sourceLayerId?: string; // required for node-level authoring; hidden from users
  label: string;
  kind: "navigate" | "invoke" | "input";
  relation?: "expand" | "reference"; // required for navigate
  targetLayerId?: string; // required for navigate; a layer may contain one node
  interactionTemplate?: {
    kind: "message" | "node-action";
    text?: string;
  };
  input?: {
    control: "text" | "single_select" | "multi_select";
    prompt: string;
    options?: Array<{ key: string; label: string }>;
    minimumSelections?: number;
  };
};
  • navigate opens an accepted layer without Complete. An expand relation develops the answer. A reference relation supplies context.
  • invoke creates one user-interaction node referring to the selected node and action, then calls Complete once.
  • input embeds a bounded text, single-select, or multi-select control in the node detail grammar. It is neither navigation nor an independent invocation.
  • The product does not expose navigate relations or authoring provenance. These fields enforce graph semantics.
  • Expand paths are recursive without a fixed depth. Reference paths do not increase expansion depth.

There is no universal Go deeper button. Deeper detail exists only when the harness authors an appropriate expand action.

Authored-action lifecycle

  1. During a Complete run, the harness authors an action in draft state on a draft or reused node.
  2. The engine validates the source, authoring layer, key, kind, relation, target, ownership, visibility, and context-specific permission.
  3. The action becomes visible only when its graph version is submitted and accepted.
  4. A navigate selection reads its target locally and does not change graph state.
  5. An invoke selection creates a new node-action interaction containing the source node ID, action ID/key, optional user text, and inherited workspace binding. That new interaction is the root of the next Complete input graph.
  6. The original action remains part of its accepted snapshot. It is not consumed or converted into the new turn.
  7. Stop or failure leaves the invoked action terminal and unresolved. It does not create an accepted result layer.
  8. Retry uses the same interaction node. Only one accepted root expand action can become that interaction's canonical output.
  9. An accepted action remains immutable. A successful invoke can gain an append-only resolution that projects navigation to its accepted result.

The root output is exactly one interaction-authored expand action. The desktop follows it after acceptance. Later selections use ordinary local navigation.

Node-authored interaction input

  • An accepted input action is immutable, node-owned, and occurrence-scoped by presenting interaction, layer, and action IDs. Reuse of the same action in another accepted occurrence is a distinct attachment choice.
  • The user may commit multiple input actions from one or more nodes before Send. Committed values are durable thread-draft attachments, remain visible while navigating, and can be detached explicitly.
  • Send is the only execution boundary. It atomically creates a new root interaction and snapshots every committed attachment into one immutable submitted-input attempt.
  • No input action is required. An empty message is valid when at least one attachment is submitted.
  • Text values preserve authored text. Select values persist stable option keys plus their accepted labels, with multi-select keys canonically ordered. The harness receives unordered prompt/control/value snapshots without product-assigned priority.
  • Failure or stop restores the attempt's attachments to the draft unless a newer commit already owns the same occurrence. The immutable attempt cannot be retried in place; the next Send creates a new root.
  • Accepted input actions retain their authored payload in V1 conversation export even when unanswered. Accepted and terminal submitted input remains readable in compact history, safe diagnostics, and export. Import assigns fresh local identities, strips execution authority and digests, and keeps imported input read-only and inert.

13.1 Evaluation boundary and data model

An evaluation execution is one harness configuration executing one harness-agnostic case through complete(inputGraph). The lower-level runner supplies synthetic product IDs. Relayer Eval uses real product IDs and persistence.

13.2.1 Project case and thread model

A project case is a compact simulation of sustained work inside one repository, not a single isolated prompt. One initial case creates three sequential product threads against the same materialized project and project graph:

13.4 Judge design

Deterministic checks always run first. The first empty-project case then uses only the six-fact structured judge defined in Section 15D.4. It does not require an operator agent, pairwise comparison, grounding rubric, repeat policy, or promotion threshold.

The first project suite adds one simulated-user judge. The judge opens the completed turn in the exact read-only production workspace, explores the response through visible controls, and grades what the product actually communicates. It does not substitute raw graph JSON, database records, or hidden node text for the rendered experience. Every qualitative rating is supported by screenshots captured during that review session.

Configuration comparison and blind pairwise judging are later evaluation-runner capabilities. When added, the judge model/version, prompt version, rubric version, repeat count, thresholds, and tie policy are recorded with the run. Human review in the real graph UX remains required before product promotion.

13.4.1 Simulated-user tool contract

The simulated-user judge receives the original request, a versioned rubric, and the read-only production review window. It also receives six graph-review tools and read-only shell access to the immutable task artifact. Shell access exists to discover facts needed to apply the rubric; only the rendered graph can prove what the user experience communicates.

Input-action quality is judged from the presented action before any operator may answer it. A text input has an intentionally empty option set; single- and multi-select inputs expose their complete authored choices. The v11 necessity counterweight penalizes questions whose answers already exist in the immutable task artifact. 13.4.4 Coverage and completion

The review-writing tools reject unrelated evidence, unknown rubric keys, mismatched screenshot state, invalid nullability, incomplete action rankings, and missing recursive dependencies immediately.

submitReview lists missing subjects when coverage is incomplete. Expansion coverage includes every layer, node, visible action, and the overall turn.

Reference traversal processes each unique layer once and follows reference actions transitively. It does not activate inherited expand, invoke, or resolved-invoke actions.

The judge still grades those visible inherited actions in their reference context.

The final artifact preserves traces, screenshots, metadata, incremental reviews, rubric version, judge configuration, and completion coverage.

The opt-in node-input round-trip proof is separate from npm run check. Its mandatory gate is deterministic. A live model must author an accepted input action. The operator must commit and Send it into a new root with provenance-exact input children. The next candidate trace must contain the exact normalized semantic input snapshot in the harness prompt. A non-gating screenshot-grounded rating records whether the next visible answer materially uses the submitted value. One paired answered/unanswered run of the same pinned case calibrates that rating. The calibration records both executions and is not repeated as a default suite cost.

When the judge finds one material missing action, affected turn criteria and the overall presentation ceiling cannot exceed 6. Repeated material omissions or one critical omission cap them at 4. These are maximums, not assigned scores: the judge still chooses and explains the score warranted by the visible experience. Historical reviews retain their native scale when viewed alone; mixed-scale multi-turn projections normalize legacy scores proportionally before aggregation.

The simulated-user judge grades only what the product made visible. Separate deterministic graders remain authoritative for graph integrity, mutation policy, repository diff, protected-file hashes, public and hidden tests, build results, and commit history. A visually strong graph cannot compensate for broken code, and correct hidden work cannot compensate for an unusable visible response.

  • no development credentials, cached eval source repositories, user graphs, source maps with secrets, or absolute developer paths.

Startup uses an app-owned data directory and a per-launch loopback port/token. The Electron main process owns app-server startup, health, cancellation, shutdown, deep-link routing, and update installation barriers.

14.5 Distribution and update acceptance

macOS distribution uses a notarized DMG for first install and a signed ZIP plus channel metadata for Electron updates. Windows x64 will use a signed NSIS installer once signing is unblocked. Artifacts are content-addressed and immutable. A mutable channel manifest is published only after its target-specific artifact, signature, checksum, platform trust proof, and smoke evidence are available.

Before promotion, a clean machine must pass these product checks:

  1. Install and start the app.
  2. Connect an agent.
  3. Run or load the basic evaluation.
  4. Open the accepted execution in Relayer Eval Product workspace.
  5. Create a normal thread with the passing configuration.
  6. Quit and reopen the app with saved state.
  7. Update from the previous production version without data loss.

16.1 Product tests without paid inference

The default suite uses a fake or replay Complete implementation. It covers:

  • every visible choice and event in Agent setup, New thread, projects, Git/worktrees, thread management, settings, updates, graph navigation, context attachment, stop, retry, and recovery;
  • desktop interaction/session assembly plus Relayer input-graph and workspace-binding assembly for messages, attached context, and node actions;
  • graph-engine read/write authorization, active-interaction token checks, schema compatibility, resolved-layer reads, and migration rules;
  • node/edge/layer/action validation, recursive submission closure, atomic acceptance, historical immutability, and exact target-layer rendering;
  • secret redaction and local persistence boundaries;
  • accessibility and visual-structure assertions for all canonical mocks.

16.2 Live evaluations

Live Codex, Prime Agent, or other model runs are opt-in, metered, and never part of the default npm run check. They run through the evaluation runner and produce immutable bundles. LLM judges are versioned and calibrated against human decisions; their scores are not treated as ground truth. Simulated-user judge runs record their complete UI interaction trace and screenshot evidence so a human can audit every qualitative finding.

16.3 Human product evaluation

Human reviewers load saved results in the desktop graph UX. They judge response clarity, important details, connections, actions, and task continuation. They do not judge raw JSON or traces. Later comparisons use one case and change only the recorded harness or model configuration.

17. V1 boundary and open decisions

17.1 Included in V1

  • local profile with Codex or API-key agent login;
  • optional direct Auth0 desktop account with a pseudonymous subject and no cloud-workspace promise;
  • one OSS monorepo containing graph-engine crates, typed clients, Node harness host, harness implementations, eval runner, Rust Relayer app server, and Electron desktop packages;
  • a harness- and provider-agnostic product contract behind the Relayer Complete interface;
  • no-folder and project-backed threads;
  • non-Git folders, local Git checkout, new worktree, and fork-to-worktree;
  • graph messages, corrective or explanatory annotations through attached context, authored node actions, recursive subthreads, turn navigation, stop, retry, and local persistence;
  • bounded read-only graph search over accepted content, layers, relationships, and paths through one shared Ladybug store;
  • Rust graph core/API, opaque session-token enforcement, and TypeScript/Python graph clients;
  • persistent Node harness host, packaged codex.basic configurations, and explicit compatibility for each supported provider and harness;
  • exact empty-project Complete evaluation, followed by multi-turn, interaction, grounding, recursive-work, and hard-task capability suites;
  • Relayer Eval dashboard, read-only production-workspace review, judge evidence, and portable candidate traces;
  • Electron packages, Developer-ID-signed macOS distribution, Windows x64 distribution, and signed desktop updates.

17.2 Excluded or deferred

  • account-backed cloud sync, remote hosting, teams, profiles, and enterprise workspace administration;
  • mandatory up-front workspace graph construction;
  • continuous background stale-node propagation;
  • self-assessment as a separate product algorithm before Complete is stable;
  • arbitrary third-party harness installation and a general-purpose pluggable harness desktop;
  • third-party conversation views, generic harness protocols, and public multi-harness conformance suites;
  • a side-by-side comparison workspace inside the production renderer;
  • Mac App Store distribution, Windows Arm, and macOS 12 or older;
  • canonical user-facing agent-activity or diagnostic-trace views.
  • a generalized public harness protocol, arbitrary harness catalog, plug-in installer, or public conformance kit;

17.3 Decisions still open

  • engine indexing and compaction implementation behind the stable read/write contract;
  • whether loopback HTTP is reachable from every supported Codex sandbox or the packaged product needs HTTP over a Unix-domain socket;
  • whether a later vector candidate source provides enough value to extend the structural search contract;
  • thresholds and calibration examples beyond the fixed first six-fact LLM-judge rubric;
  • when multiple real harness ablations justify a generalized signed configuration manifest;
  • default maximum number of Relayer-managed worktrees, whether the limit is global or per project, and the limit-reached cleanup flow;
  • exact thread archive, delete-entry, graph-retention, and remove-local-data behavior;
  • exact product persistence database, export bundle, restore, and migration format.

17.4 Current unproven requirements

  • Stop and retry controls do not have product proof.
  • Context attachment does not have product proof.
  • Local-checkout, new-worktree, fork, and worktree-cleanup flows do not have product proof.
  • Rename, archive, pin, delete-entry, move-to-project, and unsent-draft recovery do not have product proof.
  • API-key providers and operating-system secret storage do not have product proof.
  • Prime Agent does not have clean-install live-product proof.
  • The root package exports canonical complete(inputGraph); live app-server adoption of that exported seam does not yet have product proof.
  • The Eval promotion bundle and retention contract remain incomplete.
  • Windows signing, installation, and interactive updater canary remain blocked.

  1. The graph engine and API pass their package and end-to-end contracts.
  2. The TypeScript and Python clients pass their package and end-to-end contracts.

  6. The run passes deterministic and judge gates.

# Desktop 0.2.15 harness-state migration incident

- **Date:** 2026-08-27
- **Status:** Resolved in Desktop Preview 0.2.16
- **Affected release:** Desktop Preview 0.2.15
- **Impact:** Preview users with a model-selecting harness session persisted by an earlier release could not start the Relayer runtime after updating to 0.2.15.

## Summary

Desktop Preview 0.2.15 strengthened the harness boundary so a model-selected provider could not fall back to ambient credentials. The new validation was correct and failed closed, but startup applied it to persisted schema-v4 session configurations written before `executionAccessContracts` existed. Because the persisted-state schema was not advanced and no migration handled that historical shape, one old resumable harness session could stop the entire runtime from starting.

Desktop Preview 0.2.16 advances harness state to schema v5. During the v4-to-v5 migration it recognizes only the exact pre-access-contract session grammar, creates an owner-only backup, and discards that opaque provider-resume session so the trusted current catalog can register a fresh session. Product threads, graph history, and accepted work remain intact. State that does not match the narrowly recognized historical form still fails closed.

There is no evidence that credentials were exposed. The availability failure occurred because the authority safeguard rejected ambiguous old state as designed, while the upgrade path needed to make that state unambiguous was absent.

## Detection and impact

The incident was detected by a user installing 0.2.15 and reporting the startup dialog:

> Model-selecting harness configurations require executionAccessContracts so a selected provider cannot fall back to ambient credentials.

We reproduced the message locally against a temporary copy of the affected profile. The installed harness catalog itself was valid and already contained access contracts. The incompatible input was an older entry in `harness-sessions.json`.

The failure was conditional:

- Existing profiles with a pre-contract model-selecting schema-v4 harness session were affected.
- Clean profiles and sessions persisted with current contracts were not affected.
- The failure blocked runtime startup, rather than isolating the obsolete resumable session.
- Product database records, graph history, and accepted work were not damaged.

- **2026-08-27:** Desktop Preview 0.2.15 was published. A user installed it, reported the startup failure, and reproduced the same failure in a local application.

- **2026-08-27 14:03 ET:** Desktop Preview 0.2.16 completed protected validation, signing, notarization, and Preview publication for both macOS architectures in [release run 33099204564](https://github.com/vishaltandale00/relayer-graphcomplete/actions/runs/33099204564).

## Root cause

The persisted representation and the current configuration contract were treated as if they evolved together, although persisted sessions outlive the release that wrote them.

The access-contract change made the current parser stricter. Startup then parsed historical schema-v4 session bytes with that current parser before the trusted catalog could replace or migrate the session. Because the outer state version remained v4, there was no explicit signal that the inner configuration shape needed an upgrade. The security invariant correctly rejected the missing authority declaration, but the application had no safe compatibility path for the known historical state.

## Why tests and release checks did not catch it

1. The schema-v4 resume test built its supposed old configuration with current fields, including `executionAccessContracts`. It tested the version number, not the actual bytes produced by the prior release.
2. CI covered clean startup and current configuration shapes, but did not boot the current application against frozen user data from the previous Preview.
3. The engineering process did not require a persisted-schema review when a parser or authority invariant became stricter.
4. The release workflow proved source integrity, repository checks, signing, notarization, and publication. It did not include a pre-publication N-1 profile upgrade smoke.
5. There was no single release inventory of every durable store whose contents must survive an application upgrade.

## Resolution

PR [#198](https://github.com/vishaltandale00/relayer-graphcomplete/pull/198) shipped the following changes in Desktop Preview 0.2.16:

- Advanced harness persistence from schema v4 to v5.
- Added an exact recognizer for the historical pre-access-contract v4 session shape.
- Wrote an owner-only `.v4.backup` before migration.
- Removed only the obsolete opaque provider-resume session, allowing the current trusted catalog to create a fresh session.
- Preserved product threads, graph databases, accepted history, and all unrelated state.
- Kept malformed, tampered, or otherwise unrecognized authority state fail-closed.
- Added a regression fixture that omits the new field exactly as the prior release did, plus a separate corruption test that proves the migration does not weaken policy enforcement.
- Replayed the migration against a temporary copy of the reported profile and confirmed schema v5, no active obsolete session, one retained legacy backup, and mode `0600`.

## Corrective actions

### Completed

- [x] Ship the narrow schema-v5 migration and fail-closed regression coverage in 0.2.16.
- [x] Verify the migration against a temporary copy of a real affected profile without modifying the user's state.
- [x] Require protected CI before merging and publish from an immutable tag.

### Before the next Preview

- [ ] Check in secret-free golden fixtures captured from actual prior release tags for every supported persisted-state schema. Do not construct compatibility fixtures with current factories or types.
- [ ] Add an upgrade compatibility suite that boots the current runtime against N-1 and N-2 fixtures and verifies startup, existing-thread access, and a new follow-up execution.
- [ ] Add a review gate: any stricter parser, required persisted field, or authority invariant must either preserve historical parsing or advance the schema with a tested migration.
- [ ] Maintain a release inventory covering harness sessions, product SQLite data, graph SQLite data, settings, and other durable user state; exercise each store in the upgrade suite.
- [ ] Run a signed-candidate upgrade smoke before Preview publication using representative, sanitized previous-Preview user data on every published platform architecture.
- [ ] Define startup isolation rules so a narrowly recognized obsolete resumable harness session can be quarantined without making corrupt or ambiguous authority state permissive.

### Release infrastructure housekeeping

- [ ] Update pinned GitHub Actions that still target the deprecated Node.js 20 action runtime. This warning did not cause the incident, but should not remain in the release path.

## What went well

- The authority check failed closed, so the regression did not silently reintroduce ambient-credential fallback.
- The user report included the exact error and was reproducible against real persisted state.
- The repair was tested first against the actual historical shape, then against tampered state to preserve the security boundary.
- Immutable tagging, protected validation, signing, and notarization controls remained effective.

## Lessons

Persisted compatibility must be tested from historical bytes, not inferred from a schema number or reconstructed with current code. Security invariants and upgrade migrations are one change surface: strengthening an authority boundary is incomplete until every supported historical state has a deterministic fail-closed transition. Finally, a release is not upgrade-safe merely because a clean install builds, signs, launches, and publishes; the candidate must start over representative state written by the releases users actually run.
